# 4.3 Input Attributes

> **Input Attributes** هي الخصائص التي تتحكم في كيفية عمل عناصر الإدخال، وكيف يتفاعل معها المستخدم، وكيف يتحقق المتصفح من صحة البيانات قبل إرسالها.
>

# السؤال الأول

# What is the `name` attribute?

> **لنبدأ بـ `name` قبل `required`، لأنه أهم Attribute في الـ Forms، ومع ذلك كثير من المطورين يجهلون أهميته.**
> 

مثال:

```
<formaction="/login"method="post"><inputtype="email"name="email"><buttontype="submit">
        Login</button></form>
```

# الشرح بالتفصيل

دخلنا رسميًا في قسم جديد فائق الأهمية: **`4.3 Input Attributes` (خصائص عناصر الإدخال)**، وبدأنا بالعمود الفقري لأي عملية نقل بيانات في الويب: **`What is the name attribute?`**.

في المقابلات الشخصية، السؤال ده بيكشف فوراً إذا كان المطور فاهم بروتوكولات نقل البيانات وكيف تتكلم الواجهات (Frontend) مع الخوادم (Backend)، أم أنه متعود على كتابة كود مكرر بالجافاسكريبت دون فهم آليات المتصفح الافتراضية.

تعال نفصص الـ `name attribute` بأعلى عمق هندسي وبأسهل أسلوب.

## 1. التشبيه العبقري (بطاقات الأسماء على صناديق الشحن)

تخيل إنك بتنقل عفش بيتك لبيت جديد؛ جبت صناديق كرتون كتير (دي عناصر الـ `<input>`) وحطيت في الصندوق الأول شاشة التلفزيون، وفي الصندوق الثاني الكتب، وفي الصندوق الثالث الملابس.

لو قفلت الصناديق دي وشحنتها لعقد العمل الجديد بدون ما تكتب أي كلمة من برة؛ العمال لما يستلموا الصناديق هناك هيفتحوا إيديهم ويسألوك: "الصندوق ده جواه إيه؟ وده بتاع إيه؟".
الحل المنطقي والبديهي إنك بتجيب قلم وتكتب على الصندوق الأول **"الاسم: تلفزيون"**، وعلى الثاني **"الاسم: كتب"** (دي صفة الـ **`name`**).

لما الصناديق توصل، المستلم (الباكيند / السيرفر) مش محتاج يضرب الودع؛ هيقرأ الاسم المكتوب على الكرتونة من برة فيعرف فوراً يفرغ المحتوى في مكانه الصح!

## 2. الدور التقني للـ `name` خلف الكواليس (The Payload)

من الناحية البرمجية، الـ `name attribute` هو اللي بيحدد **المفتاح (Key)** في حزمة البيانات المرسلة للسيرفر، بينما ما يكتبه المستخدم يمثل **القيمة (Value)**.

عندما يضغط المستخدم على زر الإرسال (Submit)، يقوم المتصفح تلقائياً بتجميع البيانات على هيئة أزواج من **`Key=Value`** (تسمى تقنياً **Form Data** أو **Payload**).

في المثال الاحترافي والممتاز الذي أرفقته:

HTML

```
<form action="/login" method="post">
    <input type="email" name="email">
    <button type="submit">Login</button>
</form>
```

إذا كتب المستخدم في الخانة البريد الإلكتروني التالي: `user@example.com` وضغط على Login:

1. المتصفح هينظر للـ input وهيقول: "الـ `name` هنا يساوي `email` والـ `value` المكتوبة هي `user@example.com`".
2. هيحزم البيانات ويبعتها للسيرفر بالشكل ده كـ Payload:Plaintext
    
    ```
    email=user@example.com
    ```
    
3. مهندس الباكيند في السيرفر هيستقبل البيانات ويقول في كوده: `request.body.email` ليرى الإيميل مباشرة.

## 3. الفخ والتحذير المدمر (ماذا لو نسينا الـ `name`؟)

سؤال الفخ الأشهر في المقابلات: **"ماذا يحدث لو كتبت input جميل ومتنسق بالـ CSS وحطيت جواه بيانات، بس نسيت أكتب جواه `name` attribute؟"**

- **الإجابة الصارمة:** **لن يتم إرسال هذا الـ input أو قيمته إلى السيرفر نهائياً!** المتصفح سيتجاهله تماماً كأنه غير موجود وقت الإرسال، حتى لو كان مكتوباً جواه بيانات سليمة 100%.

## 4. وظيفة ثانوية رائعة: الـ Radio Buttons Grouping

للـ `name` وظيفة تانية عبقرية وسحرية مع عناصر الـ **`type="radio"`**؛ لو عندك 3 خيارات اختيار أحادي (مثل: ذكر / أنثى / أفضل عدم الإجابة)، كيف يفهم المتصفح أنه لا يجوز للمستخدم اختيار أكثر من واحد في نفس الوقت؟

- **الحل:** بنعطيهم كلهم **نفس الـ `name` بالظبط** (مثال: `name="gender"`). هنا المتصفح بيفهم إنهم عائلة واحدة وبيسمح باختيار خيار واحد فقط منهم تلقائياً!

## الكلمات المفتاحية للحفظ (Keywords)

- **`Key-Value Pairs`:** أزواج المفتاح والقيمة المرسلة للسيرفر.
- **`Form Payload`:** حزمة البيانات المشحونة عبر الشبكة.
- **`Data Serialization`:** عملية تحويل مدخلات العناصر إلى نصوص منظمة يفهمها الخادم.
- **`Radio Grouping`:** تجميع أزرار الاختيار الأحادي تحت اسم موحد.

> **جملتك النموذجية في المقابلة:**
"The **`name` attribute** is the single most important attribute for data submission in HTML forms. It acts as the **Key** (identifier) in the **Key-Value pair** sent to the server, while the user's input acts as the **Value**. Without a `name` attribute, the browser will completely **ignore** the input element and will **not** include its data in the form submission payload. Additionally, sharing the same `name` among multiple **`radio` inputs** groups them together, ensuring only one option can be selected at a time."
>

# What is the `required` attribute?

مثال

<inputtype="email"required>

# الشرح بالتفصيل

وصلنا للسؤال الثاني في قسم **`4.3 Input Attributes`**، وهو السمة المسؤولة عن حراسة وحماية البيانات قبل شحنها: **`What is the required attribute?`**.

في المقابلات الشخصية، السؤال ده بيبان سهل، لكن الـ Interviewer بيستغله عشان يفتح معاك نقاش عميق حول الـ **Client-Side Validation (التحقق من صحة البيانات من جهة العميل)** وهل نكتفي بيه ولا لأ، وإزاي المتصفح بيتصرف برمجياً بسببه.

تعال نفصص الـ `required attribute` بأعلى عمق هندسي وأسهل أسلوب.

## 1. التشبيه العبقري (موظف أمن المطار - Security Gate)

تخيل إنك مسافر وجيت تعدي من بوابة أمن المطار؛ الموظف طلب منك جواز السفر (ده الـ input).
لو جواز السفر مش معاك، أو نسيت تطلعه من الشنطة، موظف الأمن هيوقفك فوراً ويقولك: "ممنوع تعدي البوابة وتدخل الطيارة إلا لما توريني الجواز!" (الطيارة هنا هي السيرفر، وموظف الأمن هو الـ **`required` attribute**).

الـ `required` هي بوابة الأمن اللي بتمنع الفورم من إنها "تسافر" للسيرفر وتعمل Reload للصفحة طول ما الخانة دي فاضية ومكتوبة فيها صفر بيانات.

## 2. السلوك الفني والبرمجي (من كودك الممتاز)

في المثال الذكي اللي أنت كتبته:

HTML

```
<input type="email" required>
```

بمجرد إضافة كلمة `required` (وهي سمة بولية - Boolean Attribute، يعني وجودها فقط في الكود يكفي لتفعيلها بدون الحاجة لكتابة `=true`):

1. **إيقاف الإرسال تلقائياً (Block Submission):** لو المستخدم ضغط على زرار الـ Submit والخانة دي فاضية، المتصفح هيوقف عملية الإرسال تماماً في مكانها.
2. **إظهار رسالة خطأ أصيلة (Native Tooltip):** المتصفح هيطلع للمستخدم رسالة تحذيرية منبثقة بشكل افتراضي (تختلف حسب لغة المتصفح، مثل: *"Please fill out this field"* أو *"يرجى ملء هذا الحقل"*).

## 3. قوة الدمج: `required` مع الـ `type` (الذكاء المزدوج)

لاحظ في مثالك إنك دمجت `type="email"` مع `required`. المزيج ده بيخلي المتصفح يعمل حمايتين ورا بعض:

- **الأولى:** يتأكد إن الخانة مش فاضية (بفضل `required`).
- **الثانية:** يتأكد إن اللي اتكتب جواه يطابق صيغة البريد الإلكتروني الحقيقية اللي فيها `@` ونقطة (بفضل `type="email"`).

## 4. السر الهندسـي الأهم للمقابلات: هل الـ `required` تكفي وحدها؟ (فخ السنيورز!)

المقابل هيسألك فخ مصيري: **"لو أنا مطور خبيث وعايز أبعت الفورم فاضية رغم إنك كاتب `required` في الـ HTML، هل أقدر؟"**

- **الإجابة الصادمة:** نعم، وبسهولة شديدة! المطور الخبيث يقدر يفتح الـ DevTools (Inspect Element) ويمسح كلمة `required` من الكود في ثانيتين، أو يبعت البيانات مباشرة للسيرفر باستخدام أدوات زي Postman أو سكريبت جافاسكريبت خارجي يتخطى المتصفح كله.
- **القاعدة الهندسية الذهبية:**
    
    > **"Client-side validation is for UX, Server-side validation is for Security."**
    (التحقق في واجهة المستخدم بـ `required` هو لتوفير تجربة مستخدم سريعة تمنع إعادة تحميل الصفحة فوراً، لكنه لا يحمي الموقع أمنياً، ولا بد من إعادة التحقق من إجبارية البيانات مرة أخرى داخل السيرفر/الباكيند لضمان الأمان المطلق).
    > 

## الكلمات المفتاحية للحفظ (Keywords)

- **`Boolean Attribute`:** سمة منطقية (تتفعل بمجرد كتابة اسمها).
- **`Client-Side Validation`:** التحقق من صحة البيانات في المتصفح قبل الإرسال.
- **`Native Browser Tooltip`:** الرسالة التحذيرية الافتراضية للمتصفح.
- **`Server-Side Validation Bypass`:** ضرورة التحقق في السيرفر لعدم أمان واجهة المستخدم المطلق.

> **جملتك النموذجية في المقابلة:**
"The **`required` attribute** is a boolean attribute that enforces **client-side validation** by preventing the form from being submitted if the input field is empty. When triggered, the browser automatically blocks the submission and displays a **native error tooltip** to the user. While it greatly enhances the **User Experience (UX)** by providing instant feedback without a page reload, as UI Engineers we must remember that it can be easily bypassed via browser DevTools. Therefore, **server-side validation** remains mandatory for security
> 

# السؤال الثالث

# What is the `readonly` attribute?

## المثال

```
<inputvalue="Hanan Awad"readonly>
```

# الشرح بالتفصيل

وصلنا للسؤال الثالث في قسم **`4.3 Input Attributes`**، وهو السمة المسؤولة عن عرض البيانات بشكل ثابت ومحمي من التعديل: **`What is the readonly attribute?`**.

في المقابلات الشخصية، الـ Interviewer بيحب يسألك عن الـ `readonly` لسبب ذكي جداً: وهو أنه **غالباً بيقارن بينها وبين سمة تانية اسمها `disabled`** عشان يختبر مدى دقة معلوماتك وفهمك لكيفية معالجة المتصفح للبيانات عند الإرسال.

تعال نفصص الـ `readonly` بأعلى عمق هندسي وأسهل أسلوب.

## 1. التشبيه العبقري (لوحة العرض الزجاجية في المتحف)

تخيل إنك داخل متحف وشايف قطعة أثرية نادرة معروضة جوة صندوق زجاجي محكم. أنت قادر تشوف القطعة بوضوح، وتقرأ البيانات المكتوبة عليها، وتقدر تصورها كمان (ده معنى الـ **`readonly`**)، لكنك مستحيل تمد إيدك وتمسكها أو تعدل في شكلها أو تمسح جزء منها.

الصندوق الزجاجي بيسمح بـ **القراءة فقط** لكنه بيمنع التعديل والتشويه تماماً.

## 2. السلوك الفني والبرمجي (من كودك الممتاز)

في مثالك الاحترافي:

HTML

```
<input value="Hanan Awad" readonly>
```

بمجرد إضافة السمة البولية `readonly` (واللي بتتفعل بمجرد كتابة اسمها كدة):

1. **إمكانية العرض والتحديد (Selectable & Focusable):** المستخدم يقدر يضغط بالماوس جوه الـ input، ويقدر يحدد النص (Highlight) ويعمل له نسخ (Copy)، والـ Cursor (مؤشر الكتابة) هيظهر عادي، لكن لو حاول يكتب أي حرف أو يمسح أي حرف، المتصفح هيمنعه تماماً.
2. **إرسال البيانات للسيرفر (Crucial Point!):** عند الضغط على زرار الـ Submit، المتصفح **هياخد القيمة المكتوبة جوة الـ input ده (اللي هي "Hanan Awad") ويبعتها للسيرفر عادي جداً** ضمن حزمة البيانات (Payload).

## 3. المعركة الكبرى: الـ `readonly` ضد الـ `disabled` (سؤال الفخ في المقابلات!)

المقابل هيسألك فوراً: **"إيه الفرق بين readonly و disabled؟ طالما الاتنين بيمنعوا المستخدم من الكتابة؟"**

وهنا لازم تجاوب بالجدول الهندسي الدقيق ده اللي هيبهر أي حد بيقابلك:

| **وجه المقارنة** | **الـ readonly** | **الـ disabled** |
| --- | --- | --- |
| **التفاعل بالماوس والكيبورد** | يمكن تحديده (Focusable / Selectable) ونسخ النص من داخله. | لا يمكن تحديده تماماً، ويبدو باهتاً باللون الرمادي (Grayed out). |
| **إرسال البيانات (Form Submission)** | **تُرسل قيمته للسيرفر** بشكل طبيعي جداً. | **لا تُرسل قيمته نهائياً**، المتصفح يتجاهله تماماً أثناء الإرسال. |
| **متى نستخدمه؟** | عندما نريد إرسال قيمة ثابتة للسيرفر لا نريد للمستخدم تغييرها (مثل: كود عملية الشراء، أو اسم مستخدم مسجل مسبقاً). | عندما نريد تعطيل حقل مؤقتاً حتى يقوم المستخدم بخطوة أخرى (مثل: تعطيل زر الإرسال حتى يوافق على الشروط). |

## الكلمات المفتاحية للحفظ (Keywords)

- **`Read-only Status`:** حالة القراءة فقط دون السماح بالتعديل.
- **`Focusable & Selectable`:** قابل للتركيز وتحديد النص ونسخه.
- **`Form Data Inclusion`:** تضمين القيمة وإرسالها مع حزمة البيانات للسيرفر.
- **`Readonly vs. Disabled`:** الفروق الجوهرية في التفاعل والإرسال.

> **جملتك النموذجية في المقابلة:**
> 
> 
> "The **`readonly` attribute** is a boolean attribute that prevents the user from modifying the value of an input field, while still allowing them to **focus on it, select the text, and copy it**. The most critical architectural feature of `readonly` is that **its value is still submitted to the server** when the form is sent. This is the main difference compared to the **`disabled` attribute**, which completely grays out the element, prevents focus, and **excludes** its value from being sent to the server during submission."
>

وصلنا للسؤال الخامس في قسم **`4.3 Input Attributes`**، وهو السمة المسؤولة عن توفير الوقت والجهد على المستخدم ومساعدته في ملء البيانات بضغطة زر واحدة: **`What is the autocomplete attribute?`**.

في المقابلات الشخصية، السؤال ده بيكشف إذا كنت مطورًا تهتم بـ **تجربة المستخدم (User Experience - UX)** وتسهيل رحلته داخل الموقع، خصوصاً على الموبايل حيث تكون الكتابة صعبة ومملة، أم أنك تترك الأمور الافتراضية للمتصفح دون تحسين.

تعال نفصص الـ `autocomplete attribute` بأعلى عمق هندسي وأسهل أسلوب.

## 1. التشبيه العبقري (مساعد الكتابة الذكي أو السكرتير الشخصي)

تخيل لو عندك سكرتير شخصي ذكي جداً، حافظ اسمك بالكامل، وإيميلك، وعنوان بيتك، وحتى أرقام كروت الائتمان بتاعتك.
كل ما تيجي تملا استمارة ورقية، أول ما يلاقيك هتمسك القلم وتكتب "الاسم"، يقوم شادد القلم منك وكاتب اسمك ثواني، ولما تروح لخانة "العنوان" يكتبهالك في لحظة.

الـ **`autocomplete`** هو السكرتير الشخصي ده جوه المتصفح! هو اللي بيقول للمتصفح: "يا متصفح، ساعد المستخدم واقترح عليه البيانات اللي هو خزنها عندك مسبقاً عشان يملى الخانة دي بضغطة واحدة بدل ما يكتبها حرف حرف".

## 2. الشرح الفني والبرمجي (من أمثلتك الاحترافية)

في المثالين الممتازين اللي أنت كتبتهم، أنت وضحت طريقتين للتحكم في الميزة دي:

### الحالة الأولى: التحديد الدقيق لنوع البيانات (المثال الأول)

HTML

```
<input type="email" autocomplete="email">
```

- **الشرح الهندي:** هنا أنت بتقول للمتصفح بشكل صريح ومحدد: "الخانة دي مخصصة للبريد الإلكتروني".
- **النتيجة:** المتصفح مش هيقترح أي كلام عشوائي اتكتب قبل كده؛ بل هيقترح فقط **عناوين البريد الإلكتروني الفسيولوجية المسجلة في ملف المستخدم الشخصي** (Autofill profile).
- **قيم شائعة أخرى:**
    - `autocomplete="username"` (لإدخال اسم المستخدم).
    - `autocomplete="current-password"` (لتسهيل جلب كلمة المرور الحالية من مدير كلمات المرور كـ 1Password أو Google Chrome Passwords).
    - `autocomplete="new-password"` (عند تسجيل حساب جديد لكي يقترح المتصفح كلمة مرور قوية تلقائياً).

### الحالة الثانية: الإغلاق التام للميزة (المثال الثاني)

HTML

```
<form autocomplete="off">
```

- **الشرح الهندي:** هنا أنت حطيت السمة على مستوى الـ `<form>` بالكامل وقيمتها `off`. ده معناه: "يا متصفح، امنع تماماً حفظ أو اقتراح أي بيانات اتكتبت جوة الفورم دي".
- **متى نستخدمها؟** نستخدمها لأسباب أمنية صارمة أو خصوصية عالية، مثل:
    - شاشات المعاملات البنكية (Online Banking).
    - خانات إدخال الرموز السرية لمرة واحدة (OTP - One Time Password).
    - الأجهزة العامة أو المشتركة لمنع المتصفح من تخزين بيانات حساسة للمستخدمين.

## 3. الأهمية القصوى للـ Accessibility والـ Mobile UX

أنت كـ UI Engineer شاطر، لازم تلفت نظر المقابل للفوائد دي:

1. **تقليل نسبة التخلي عن الفورم (Form Abandonment):** كل ما الفورم كانت أسهل وأسرع في الملء، كل ما المستخدم كملها للآخر وممشيش من الموقع. الـ `autocomplete` بيقلل وقت ملء الفورم بنسبة تصل لـ 30%.
2. **توافقية الـ Password Managers:** كتابة الـ `autocomplete` الصح بتخلي برامج حفظ كلمات المرور (زي Dashlane وBitwarden) تفهم الخانات بدقة وتملى البيانات تلقائياً للمستخدم دون أي تعقيد.

## الكلمات المفتاحية للحفظ (Keywords)

- **`Browser Autofill`:** ميزة الإكمال التلقائي للمتصفح.
- **`Password Managers Integration`:** التكامل مع مديري كلمات المرور.
- **`Form Abandonment Reduction`:** تقليل نسبة تراجع وهروب المستخدمين من ملء النماذج.
- **`Security & Privacy Controls`:** ضوابط الأمان والخصوصية (باستخدام `autocomplete="off"`).

> **جملتك النموذجية في المقابلة:**
"The **`autocomplete` attribute** is a vital UX tool that helps the browser or password managers predict and auto-fill user inputs (like emails, addresses, or passwords) based on previously saved data. By specifying values like **`autocomplete="email"`**, we guide the browser to suggest the exact right category of data. Conversely, we can set **`autocomplete="off"`** on sensitive forms, such as banking inputs or OTP fields, to prevent the browser from caching and suggesting highly confidential information, balancing great **User Experience (UX)** with **data security**."
>

# الشرح بالتفصيل

السؤال السادس

What is the placeholder attribute?    المثال

type="email"

وصلنا للسؤال السادس في قسم **`4.3 Input Attributes`**، وهو السمة البصرية الأكثر شهرة وجدلاً في عالم تصميم واجهات الويب: **`What is the placeholder attribute?`**.

في المقابلات الشخصية، السؤال ده بيبان بسيط جداً، لكن الـ Interviewer بيحب يستغله لفتح نقاش عميق حول **تجربة المستخدم (UX)** و**إمكانية الوصول (Accessibility - a11y)**؛ لأن الـ `placeholder` سلاح ذو حدين، واستخدامه الخاطئ ممكن يدمر تجربة الاستخدام تماماً!

تعال نفصص الـ `placeholder attribute` بأعلى عمق هندسي وبأسهل أسبوب.

## 1. التشبيه العبقري (الكتابة الخفيفة بالرصاص في كراسة الرسم)

تخيل لو بتعلم طفل صغير الرسم أو الكتابة؛ فبتجيب كراسة وتكتب له الحروف أو الأشكال بخط رمادي خفيف جداً بالقلم الرصاص (ده الـ **`placeholder`**)، وتقول له: "اكتب فوق الخط ده".
بمجرد ما الطفل يمسك القلم الجاف ويبدأ يكتب أول حرف حقيقي، الخط الرمادي الخفيف اللي تحت بيختفي تماماً وتظهر كتابة الطفل بس.

الـ `placeholder` هو النص المرشد الخفيف ده جوه الـ input؛ وظيفته يديك "تلميح سريع" عن شكل البيانات المطلوبة، وبيختفي فوراً بمجرد ما تبدأ تكتب أول حرف.

## 2. السلوك الفني والبرمجي (من كودك الممتاز)

في مثالك الواضح والجميل:

HTML

```
<input type="email" placeholder="Enter your email">
```

بمجرد استخدام السمة دي:

1. **عرض نص مؤقت (Temporary Hint):** المتصفح بيعرض النص الرمادي `"Enter your email"` داخل الخانة طالما أنها فارغة.
2. **الاختفاء الفوري عند الكتابة:** بمجرد ما المستخدم يضغط على الـ input ويكتب حرف واحد فقط، النص المؤقت ده بيختفي تماماً. ولو مسح الكلام ورجعت الخانة فاضية، الـ placeholder بيرجع يظهر تاني تلقائياً.

## 3. التحذير الهندسي الحرج: فخاخ الـ `placeholder` (سؤال السينيرز في الـ UX!)

المقابل هيسألك فوراً: **"هل ينفع نستخدم الـ placeholder كبديل لعنصر الـ `<label>` عشان نوفر مساحة في التصميم؟"**
وهنا إجابتك الهندسية الصارمة لازم تكون: **"لا، إطلاقاً! وده أكبر فخ بيقع فيه المطورين."** لثلاثة أسباب رئيسية:

1. **إرهاق الذاكرة المؤقتة (Short-term Memory Strain):** لو المستخدم بدأ يكتب، الـ placeholder هيختفي. لو جاله تليفون أو تشتت ورجع يبص على الشاشة، مش هيفتكر الخانة دي كانت بتاعة إيه (هل كانت بتاعة البريد الإلكتروني الشخصي ولا بريد العمل؟) لأنه مفيش `<label>` ثابت فوق الخانة يشرح له هي إيه!
2. **مشاكل إمكانية الوصول (Accessibility/Contrast):** لون الـ placeholder الافتراضي بيكون رمادي فاتح جداً. الأشخاص اللي عندهم مشاكل في الرؤية مش بيقدروا يشوفوه بسبب ضعف التباين البصري (Low Contrast). كما أن بعض مساعدات القراءة (Screen Readers) لا تقرأ الـ placeholder بوضوح كبديل للـ `<label>`.
3. **الخلط البصري (Confusion):** بعض المستخدمين (خصوصاً كبار السن) بيفكروا إن الـ input مكتوب جواه بيانات جاهزة فعلاً بسبب وجود الـ placeholder، فبيسيبوا الخانة فاضية ويمشوا!

## 4. كيف نستخدمه بشكل صحيح كـ UI Engineers؟

القاعدة الذهبية:

> **"The placeholder is for hints (examples), NOT for labels (titles)."**
(الـ placeholder معمول عشان يديك مثال على شكل البيانات، مش عشان يقولك اسم الخانة إيه).
> 
- **استخدام خاطئ:** `<input placeholder="First Name">` (بدون وجود label).
- **استخدام هندسي صحيح 100%:**HTML
    
    ```
    <label for="email">Email Address</label>
    <input id="email" type="email" placeholder="alex@example.com">
    ```
    
    *(هنا الـ Label واضح وثابت وهو "Email Address"، والـ placeholder بيساعد المستخدم بمثال عملي لشكل الإيميل المطلق).*
    

## الكلمات المفتاحية للحفظ (Keywords)

- **`Temporary Hint`:** تلميح مؤقت يختفي عند الكتابة.
- **`Placeholder vs. Label`:** الفرق بين التلميح المؤقت والتسمية الثابتة.
- **`Accessibility & Contrast Issues`:** مشاكل سهولة الوصول وضعف تباين الألوان.
- **`Short-term Memory Strain`:** إرهاق الذاكرة اللحظية للمستخدم عند اختفاء النص.

> **جملتك النموذجية في المقابلة:**
"The **`placeholder` attribute** provides a temporary, light-gray hint or example inside an input field when it is empty. However, as UI Engineers, we must **never use placeholder as a replacement for the `<label>` element**. Doing so hurts **accessibility (a11y)**, causes **short-term memory strain** because the hint disappears once the user starts typing, and can confuse users with low vision due to low color contrast. Instead, we should always pair the input with a visible `<label>` and use the placeholder solely to show an example of the expected data format (like `alex@example.com` for an email input)
> 

# السؤال السابع

# What is the `pattern` attribute?

## المثال

```
<inputtype="text"pattern="[A-Za-z]{3,}">
```

# الشرح بالتفصيل

وصلنا للسؤال السابع في قسم **`4.3 Input Attributes`**، وهو السمة الأكثر قوة وذكاءً للتحقق من البيانات مباشرة في الواجهة الأمامية دون الحاجة لكتابة سطر جافاسكريبت واحد: **`What is the pattern attribute?`**.

في المقابلات الشخصية، هذا السؤال يكشف عما إذا كنت تتقن أدوات الـ HTML الأصلية (Native HTML Validation) وتعرف كيف تحمي خوادم موقعك وقواعد البيانات من المدخلات العشوائية، ويوضح مدى فهمك لمفهوم التعبيرات المنتظمة (Regular Expressions).

تعال نفصص الـ `pattern attribute` بأعلى عمق هندسي وبأسهل أسلوب.

## 1. التشبيه العبقري (حارس الأمن وبوابة القياس)

تخيل أنك تقف على بوابة مصنع كراسي، ولديك قالب حديدي مفرغ على شكل كرسي محدد الأبعاد. وظيفتك كحارس أمن هي فحص أي منتج يمر عبر البوابة:

- إذا مر الكرسي داخل القالب تماماً بدون زيادة أو نقصان 👈 يُسمح له بالمرور.
- إذا كان الكرسي أكبر، أو أصغر، أو جاء أحدهم بطاولة بدلاً من الكرسي 👈 تمنعه فوراً وتقول له: "هذا لا يطابق القالب المطلوب!".

الـ **`pattern`** هو هذا القالب الحديدي! أنت تعطي المتصفح "صيغة أو شكل محدد" (قالب)، وتقول له: "لا تقبل هذه الـ Form ولا تدعها تُرسل إلى السيرفر إلا إذا كان النص الذي كتبه المستخدم يطابق هذا القالب حرفياً".

## 2. التحليل البرمجي والتفكيك الهندسي (من كودك الممتاز)

في مثالك القوي:

HTML

```
<input type="text" pattern="[A-Za-z]{3,}">
```

هنا السمة `pattern` تأخذ قيمة مكتوبة بلغة الـ **Regex (Regular Expressions)**. تعال نفكك الشفرة المكتوبة بين علامتي التنصيص لنفهم ماذا طلبت من المتصفح بالضبط:

- **`[A-Za-z]`**: هذا الجزء يعني "نطاق الحروف المسموحة". طلبت من المتصفح قبول الحروف الإنجليزية الكبيرة (`A-Z`) والحروف الصغيرة (`a-z`) فقط. (يمنع تماماً كتابة الأرقام، الرموز مثل `@` أو `#`، وحتى المسافات).
- **`{3,}`**: هذا الجزء يتحكم في "العدد أو الطول" (Quantifier). الفاصلة بعد الرقم 3 تعني: **"3 أحرف على الأقل، ومفتوحة لأي عدد أكبر"**. (3 أو أكثر).

**النتيجة العملية:**

- إذا كتب المستخدم `abc` 👈 **مقبول** (3 حروف إنجليزية).
- إذا كتب `Frontend` 👈 **مقبول** (8 حروف إنجليزية).
- إذا كتب `hi` 👈 **مرفوض** (أقل من 3 حروف).
- إذا كتب `abc1` 👈 **مرفوض** (يحتوي على رقم).

## 3. الأهمية القصوى في المقابلات (Native Form Validation)

عندما يسألك المقابل عن فائدة الـ `pattern`، ركز على النقاط الهندسية التالية:

1. **التحقق الفوري عند الإرسال (Client-side Validation):** المتصفح يمنع إرسال النموذج (Form Submission) تلقائياً إذا كانت البيانات غير مطابقة للـ pattern، ويعرض رسالة خطأ افتراضية للمستخدم (Tooltip).
2. **تحسين الأداء (Performance):** يوفر عليك كتابة دوال جافاسكريبت معقدة وعمل `Event Listeners` لمراقبة ما يكتبه المستخدم حرفاً بحرف، فالـ HTML يقوم بكل العمل خلف الكواليس بسرعة وبأقل استهلاك للموارد.
3. **أشهر حالات الاستخدام في المشاريع الحقيقية:**
    - **أرقام الهواتف:** تحديد نمط مثل `[0-9]{11}` للتأكد من أن رقم الهاتف يتكون من 11 رقماً بالضبط.
    - **الرموز البريدية (Postal Codes):** مثل خمسة أرقام متتالية `\d{5}`.
    - **بطاقات الائتمان:** التأكد من إدخال 16 رقماً مقسمة بشكل معين.

## 💡 لمسة المحترفين: كيف ترفع جودة تجربة المستخدم مع الـ Pattern؟

المتصفح إذا وجد مدخلاً خاطئاً سيعرض رسالة مبهمة للمستخدم تقول: *"Please match the requested format"*. المستخدم لن يفهم ما هو الشكل المطلوب!
لذلك، كمهندس واجهات محترف، يجب دائماً دمج سمة **`title`** مع سمة `pattern`.

HTML

```
<input
    type="text"
    pattern="[A-Za-z]{3,}"
    title="Please enter at least 3 English letters. Numbers and spaces are not allowed.">
```

*وظيف الـ `title` هنا:* المتصفح سيأخذ هذا النص ويعرضه داخل رسالة الخطأ للمستخدم ليشرح له بوضوح كيف يصحح خطأه.

## الكلمات المفتاحية للحفظ (Keywords)

- **`Regular Expressions (Regex)`**: التعبيرات المنتظمة المستخدمة لصياغة النمط.
- **`Native Validation`**: التحقق الأصلي من البيانات المدعوم من المتصفح مباشرة.
- **`Form Submission Prevention`**: منع إرسال النموذج في حال عدم التطابق.
- **`The title Attribute Complement`**: استخدام سمة `title` لتوضيح رسالة الخطأ.

> **جملتك النموذجية في المقابلة:**
"The **`pattern` attribute** is a powerful native HTML validation tool that uses **Regular Expressions (Regex)** to define a specific format that the input value must match before the form can be submitted. For instance, **`pattern="[A-Za-z]{3,}"`** restricts the input to only English letters with a minimum length of 3 characters. It is highly efficient because it handles client-side validation instantly without needing custom JavaScript. To ensure a great **User Experience (UX)**, we should always pair it with the **`title` attribute** to provide a clear, helpful error message explaining the required format to the user
> 

لدي سؤال هنا انهي افضل استخدام ال pattern  الخاص بالجافاسكريبت ام ال HTML

هذا واحد من أذكياء الأسئلة وأكثرها طرحاً في نقاشات المعمارية البرمجية (Architecture)! والسؤال الحقيقي مش مين "أفضل" بشكل مطلق، بل **"كيف ندمجهم معاً لتحقيق أفضل تجربة مستخدم وأعلى مستوى أمان؟"**.

لو أجبرنا على الاختيار أو المقارنة، فلكل واحد منهما دور هندسي محدد. تعال نفصل المميزات والعيوب لكل طرف عشان تعرف تجاوب بثقة في المقابلات:

## 1. الـ Pattern الخاص بـ HTML (خط الدفاع الأول والـ UX)

الـ `pattern` في الـ HTML يمثل الـ **Declarative Validation** (التحقق الإعلاني)؛ أنت فقط تعلن عن النمط، والمتصفح يتولى التنفيذ بالكامل.

### 👍 المميزات:

- **الأداء الخارق (Performance):** أسرع بمليون مرة لأنه يشتغل بلغة المتصفح الأصلية (C++‎ مثلاً خلف الكواليس)، ولا يستهلك أي ذاكرة من الجافاسكريبت.
- **بدون كود (Zero Code):** لا تحتاج لكتابة `Event Listeners` مثل `oninput` أو `onchange` ومراقبة الحروف وتحديث الـ UI بنفسك.
- **تجربة مستخدم سريعة (Instant UX):** يمنع إرسال الفورم فوراً ويظهر رسالة تحذيرية للمستخدم في أجزاء من الثانية.

### 👎 العيوب:

- **ضعيف أمنياً (Easily Bypassed):** أي مستخدم يفتح الـ DevTools يمكنه مسح السمة `pattern` من العنصر في ثانيتين وإرسال بيانات تالفة.
- **صعوبة التخصيص (Limited Styling/UI):** رسائل الخطأ الافتراضية للمتصفحات (Tooltips) شكلها بدائي وصعب جداً تلوينها أو جعلها تتماشى مع الهوية البصرية المخصصة لموقعك (Custom Design).

## 2. الـ Pattern الخاص بـ JavaScript (التحكم المطلق والـ Logic)

الـ JavaScript يمثل الـ **Imperative Validation** (التحقق الأمرّي)؛ حيث تكتب كوداً خطوة بخطوة للتحقق من النص باستخدام كائنات الـ `RegExp` (مثل `regex.test(value)`).

### 👍 المميزات:

- **مرونة وتحكم لا نهائي:** يمكنك فحص النص أثناء الكتابة مباشرة (Real-time Validation)، وإظهار رسائل خطأ مخصصة، متحركة، وبتصميم مبهر يتغير لونه من الأحمر للأخضر فوراً.
- **تحقق معقد (Complex Logic):** يمكنك عمل شروط لا يمكن للـ HTML فعلها وحده؛ مثل: "إذا اختار المستخدم دولة مصر، تأكد أن نمط الهاتف يبدأ بـ 01، وإذا اختار السعودية تأكد أنه يبدأ بـ 05".

### 👎 العيوب:

- **استهلاك الموارد:** تحميل ملفات جافاسكريبت إضافية وتشغيل الـ Event Listeners مع كل حركية أو حرف يكتبه المستخدم يستهلك من معالج الجهاز (CPU)، خاصة على الهواتف الضعيفة.

## ⚖️ المقارنة الهندسية السريعة (خلاصة الفروق)

| وجه المقارنة | الـ HTML Pattern | الـ JavaScript Pattern |
| --- | --- | --- |
| **السرعة والأداء** | خفيف جداً ولا يستهلك موارد. | أثقل نسبياً ويعتمد على حجم الكود. |
| **التصميم ورسائل الخطأ** | افتراضية وصعبة التعديل (Native). | مرنة تماماً ويمكن مطابقتها لأي تصميم. |
| **الأمان** | ضعيف (يمكن حذفه من المتصفح). | متوسط (يمكن تخطيه أيضاً إن لم يكن هناك فحص في السيرفر). |
| **تفاعل لحظي (Real-time)** | يحدث فقط عند محاولة الـ Submit. | يمكن تفعيله مع كل حرف يكتبه المستخدم. |

## 🏆 القرار الهندسي الصائب (The Golden Practice)

في المشاريع الاحترافية والشركات الكبرى، الإجابة النموذجية هي: **نحن نستخدم الاثنين معاً!** ونسير على استراتيجية تسمى تدرج الدفاعات:

1. **الـ HTML Pattern:** نضعه دائماً كقاعدة أساسية لضمان أداء سريع ولحماية الفورم بأقل مجهود في حال تعطل الجافاسكريبت لأي سبب في متصفح المستخدم.
2. **الـ JavaScript Pattern:** نستخدمه فوق الـ HTML لتوليد تجربة مستخدم مذهلة (تلوين الحقول بالأحمر/الأخضر، إظهار رسائل مخصصة تحت الحقل بدلاً من الـ Tooltip الافتراضية المقيدة).
3. **الـ Server-Side (الباكيند):** (وهذا أهم سطر!) نضع نفس الـ Pattern للمرة الثالثة والأخيرة داخل السيرفر، لأنها النقطة الوحيدة التي لا يمكن للمستخدم التلاعب بها أو اختراقها.

> **جملتك المختصرة للمقابل:**
"الـ HTML pattern ممتاز جداً للأداء وتوفير تجربة مستخدم سريعة وبسيطة بدون كود. لكن الجافاسكريبت يتفوق عندما نحتاج لتصميم رسائل خطأ مخصصة أو فحص تفاعلي لحظي (Real-time validation). في المشاريع الحقيقية، نستخدم الـ HTML كخط دفاع أول، والـ JS لتحسين الـ UX، مع الاعتماد الكلي على الـ Server-side للتحقق الأمني المطلق."

في المقابلات الشخصية، السمة دي بتبان بسيطة، لكن الـ Interviewer بيحب يسألها عشان يشوف مدى فهمك لكيفية تقييد مدخلات المستخدم ومنعه من الوقوع في الأخطاء المنطقية (Logical Errors) مباشرة من واجهة المستخدم.

تعال نفصص الـ `min attribute` بأعلى عمق هندسي وأسهل أسلوب.

## 1. التشبيه العبقري (حارس بوابة السينما - Age Restriction)

تخيل لو أنت رايح دار عرض سينمائي بتعرض فيلم رعب ومكتوب على البوابة لافتة ضخمة: "+18" (ده الـ **`min="18"`**).
وظيفة حارس الأمن الواقف على البوابة إنه يطلب بطاقتك؛ لو لقى سنك 15 أو 16 سنة، هيمنعك من الدخول فوراً ويقولك: "عذراً، لا يمكنك العبور، السن الأصغر المسموح به هنا هو 18 سنة!".

الـ `min` هو حارس البوابة اللي بيمنع المتصفح من قبول أي رقم أقل من القيمة المحددة له.

## 2. السلوك الفني والبرمجي (من كودك الممتاز)

في مثالك الواضح والمباشر:

HTML

```
<input type="number" min="18">
```

بمجرد استخدام السمة دي مع الـ `type="number"`، بيحصل الآتي خلف الكواليس:

1. **التحقق الأصيل (Native Validation):** لو المستخدم كتب رقم أقل من 18 (مثلاً 17) وضغط على زرار الـ Submit، المتصفح هيوقف الإرسال تلقائياً ويطلع رسالة خطأ (Tooltip) بتقول: *"Value must be greater than or equal to 18"*.
2. **التحكم في أزرار الزيادة والنقصان (Spinners):** المتصفح بيوفر أزرار سهم لأعلى ولأسفل داخل الـ input؛ لو المستخدم فضل يضغط على السهم لأسفل عشان يقلل الرقم، العداد هيقف تماماً عند الرقم **18** ومش هينزل تحته برمجياً من خلال الأسهم.

## 3. اتساع الصلاحيات: استخدام الـ `min` مع التواريخ (Dates)

مهم جداً تبهر المقابل بإنك تذكر إن الـ `min` مش بس للأرقام، دي ليها قوة خارقة مع التواريخ والأوقات (`type="date"`):

- لو بتعمل موقع لحجز تذاكر طيران أو فنادق، مينفعش المستخدم يحجز رحلة بتاريخ مبارح أو السنة اللي فاتت!
- **الحل الهندسي:** بنكتب كدة:HTML
    
    ```
    <input type="date" min="2026-07-14">
    ```
    
    *(المتصفح تلقائياً هيقفل ويعطل "Gray out" كل الأيام والشهور السابقة للتاريخ ده في قائمة النتيجة التفاعلية، وبالتالي المستخدم مستحيل يختار تاريخ قديم بالخطأ!).*
    

## الكلمات المفتاحية للحفظ (Keywords)

- **`Minimum Value Restriction`:** تقييد الحد الأدنى للقيمة.
- **`Native Number Spinner Control`:** التحكم في أزرار عداد الأرقام الافتراضية.
- **`Date Constraints`:** فرض قيود على التواريخ الزمنية لمنع الاختيارات السابقة.
- **`Logical Error Prevention`:** حماية واجهة المستخدم من الأخطاء المنطقية.

> **جملتك النموذجية في المقابلة:**
"The **`min` attribute** is used to set the lower limit or minimum value acceptable for an input field. It works perfectly with numeric types like `type="number"` to block users from entering values below the threshold, and it constrains the native browser browser spinners. Crucially, it is also used with **`type="date"`** in real-world projects—such as booking systems—to grey out past dates, preventing logical errors and enhancing **User Experience (UX)** through native browser validation
> 

اذا انا هاستخدم هذا مثلا <input type="date" min="2026-07-14">  بناءا ع اي هحدد التاريخ مش كدا هيكون استاتيك ؟

سؤال ذكي جداً وفي قلب الهندسة البرمجية! تفكيرك سليم 100%؛ لو كتبنا التاريخ كدة: `min="2026-07-14"` هيكون **ثابت (Static)**، وده معناه إن المستخدم لو فتح الموقع بكره (15 يوليو مثلاً)، المتصفح هيفضل يسمح له يختار يوم 14 يوليو اللي هو أصبح تاريخاً قديماً بالنسة لبكره!

في المشاريع الاحترافية، **مستحيل نكتب التاريخ الاستاتيكي ده بإيدينا في كود الـ HTML**.

بدل من كدة، بنخليه **ديناميكي (Dynamic)** بحيث يتغير تلقائياً مع كل ثانية وكل يوم جديد يمر. وبنعمل ده بطريقتين على حسب معمارية مشروعك:

## الطريقة الأولى: باستخدام JavaScript (الأشهر والأبسط في الـ Frontend)

بنخلي الجافاسكريبت يسأل جهاز المستخدم فوراً: *"النهارده كام في الشهر؟"*، وياخد التاريخ ده ويحقنه برمجياً جوه صفة الـ `min`.

### الكود العملي:

HTML

```
<!-- الـ input في الـ HTML بيكون نظيف وبدون تاريخ ثابت -->
<input type="date" id="booking-date">

<script>
  // 1. هنجيب التاريخ الحالي للجهاز
  const today = new Date();

  // 2. هنحوله للصيغة القياسية اللي بيفهمها الـ HTML وهي (YYYY-MM-DD)
  const yyyy = today.getFullYear();
  const mm = String(today.getMonth() + 1).padStart(2, '0'); // الشهور بتبدأ من 0
  const dd = String(today.getDate()).padStart(2, '0');

  const formattedToday = `${yyyy}-${mm}-${dd}`; // النتيجة: 2026-07-14

  // 3. هنحقن التاريخ ده في الـ min attribute للـ input
  document.getElementById('booking-date').min = formattedToday;</script>
```

**الميزة هنا:** الكود ده ديناميكي تماماً؛ لو المستخدم فتح موقعك بكره، الكود هيشتغل لوحده وهيخلي الـ `min` تلقائياً `2026-07-15`.

## الطريقة الثانية: باستخدام الـ Server-Side Rendering (مثل Next.js, Laravel, Node.js)

لو أنت شغال بـ Framework بيقوم برسم وتوليد الـ HTML على السيرفر قبل ما يبعته للمتصفح، بنخليه يحقن تاريخ اليوم مباشرة أثناء بناء الصفحة.

- **مثال بـ PHP / Laravel:**HTML
    
    ```
    <input type="date" min="{{ date('Y-m-d') }}">
    ```
    
- **مثال بـ Node.js / EJS:**HTML
    
    ```
    <input type="date" min="<%= new Date().toISOString().split('T')[0] %>">
    ```
    

**الميزة هنا:** الصفحة هتوصل لمتصفح المستخدم جاهزة بالـ `min` الخاص بتاريخ السيرفر الحالي، ومفيش أي حاجة هتحتاج تتعدل بالجافاسكريبت عند العميل.

> **خلاصة الرد الهيكلي في المقابلة:**
"كتابة التاريخ بشكل يدوي في الـ `min` يجعله Static وغير مفيد. لذلك في المشاريع الحقيقية نجعل التاريخ **Dynamic**؛ إما بحقنه برمجياً في الـ DOM باستخدام **JavaScript** عبر كائن الـ `Date` وتنسيقه بصيغة `YYYY-MM-DD`، أو بتوليده مباشرة من **السيرفر** قبل إرسال الصفحة للمستخدم، لضمان تحديث القيود تلقائياً كل يوم."
>

وصلنا للسؤال الثاني في قسم **`4.3 Input Attributes (Part 2)`**، وهو السمة الرائعة التي تتحكم في معدل التغير أو قفزات الأرقام والتواريخ: **`What is the step attribute?`**.

في المقابلات الشخصية، يحب الـ Interviewer طرح هذا السؤال ليرى مدى إدراكك للتفاصيل الدقيقة لـ HTML5 Validation وكيف تمنع المستخدم من إدخال قيم عشوائية لا تتناسب مع منطق العمل (Business Logic) الخاص بالمشروع.

تعال نفصص الـ `step attribute` بأعلى عمق هندسي وبأسهل أسلوب.

## 1. التشبيه العبقري (سُلم الصعود ومصعد الأبراج)

تخيل لو أنك تصعد على سلم؛ درجات السلم متساوية والارتفاع ثابت. مستحيل أن تقف بقدمك "بين" درجتين في الهواء! إما أن تقف على الدرجة الأولى، أو تقفز لتقف على الدرجة الثانية مباشرة.
كذلك لو ركبت مصعداً في برج سكني؛ المصعد يقف فقط في الأدوار (الدور 5، الدور 10، الدور 15) بناءً على برمجته، ولا يمكن أن يفتح الباب في منتصف الدور الثامن مثلاً!

الـ **`step`** في الـ HTML هو مقدار هذه الدرجة أو القفزة. أنت تقول للمتصفح: **"اقفز بمقدار كذا فقط، ولا تقبل أي قيمة تقع في المنتصف بين هذه القفزات"**.

## 2. التحليل البرمجي والتفكيك الهندسي (من كودك الممتاز)

في مثالك المثالي والواضح جداً:

HTML

```
<input type="number" min="0" max="100" step="5">
```

بمجرد دمج الـ `step="5"` مع الحد الأدنى والحد الأقصى، تحدث ثلاثة أشياء مهمة خلف الكواليس:

1. **القيم المقبولة برمجياً (Valid Values):** المتصفح سيحسب القيم المقبولة كالتالي: تبدأ من الـ `min` وهو (0)، ثم يضيف قيمة الـ `step` بشكل تراكمي:
    
    Valid Values=0,5,10,15,20,…,95,100
    
2. **سلوك الـ Spinners (الأسهم):** عندما ينقر المستخدم على السهم لأعلى لزيادة الرقم، فلن يتغير الرقم بمقدار 1 (مثل 0→1→2)؛ بل سيقفز بمقدار 5 مباشرة (0→5→10→15).
3. **التحقق الأصيل عند الإرسال (Validation):** لو كتب المستخدم رقماً يدوياً من لوحة المفاتيح لا يقبل القسمة على 5 (مثل **`13`**)، بمجرد الضغط على Submit سيمنعه المتصفح تماماً وتظهر رسالة خطأ صريحة: *"Please enter a valid value. The two nearest valid values are 10 and 15."*

## 3. متى نستخدم الـ `step` في المشاريع الحقيقية؟

لإبهار المقابل، اذكر له هذه الحالات العملية الحية:

- **مواقع التجارة الإلكترونية (E-commerce):** لو كنت تبيع منتجاً في مجموعات أو رزم (مثل رزم الأقلام المكونة من 12 قلماً)، تكتب:
`<input type="number" min="12" step="12">`. هنا المستخدم مجبر على شراء 12، 24، 36... وهكذا.
- **العملات والكسور العشرية (Floats):** افتراضياً، الـ `<input type="number">` لا يقبل إلا الأرقام الصحيحة (Integers). لو حاول المستخدم كتابة قيمة عشرية مثل `10.5` فسيمنعه المتصفح!
    - **الحل السحري:** نكتب `step="0.1"` للسماح بالكسور العشرية البسيطة، أو نكتب **`step="any"`** لإخبار المتصفح بأننا نقبل أي كسر عشري بدون قيود على الإطلاق!
- **تحديد الوقت والـ Schedulers (`type="time"`):** لو كنت تبني نظام حجز مواعيد عيادات طبية وتريد حجز المواعيد كل ربع ساعة فقط، يمكنك استخدام `step="900"` (الـ step في الوقت يُحسب بالثواني، و900 ثانية تعني 15 دقيقة بالضبط!).

## الكلمات المفتاحية للحفظ (Keywords)

- **`Granularity Control`:** التحكم في دقة وتفاصيل تدرج القيم.
- **`Value Increments / Decrements`:** مقدار الزيادة أو النقصان عند التفاعل.
- **`Step="any" Attribute`:** تفعيل قبول الكسور العشرية المطلقة بدون قيود.
- **`Native HTML Math Validation`:** التحقق الرياضي التلقائي الذي يقوم به المتصفح.

> **جملتك النموذجية في المقابلة:**
"The **`step` attribute** specifies the legal number intervals or granularity for an input element. In the example **`step="5"`** with **`min="0"`**, the browser will restrict valid entries strictly to multiples of 5 (like 0, 5, 10). It modifies the behavior of the input's native up/down arrows to jump by 5, and blocks form submission if a user types an invalid step value (like 13). As UI Engineers, we also use **`step="any"`** to allow decimal values in numeric inputs, which is a common fix for handling currencies or custom fractional numbers."
>

# الشرح بالتفصيل

وصلنا للسؤال الرابع في قسم **`4.3 Input Attributes (Part 2)`**، وهو خط الدفاع الأول لحماية كلمات المرور وضمان جودة نصوص المدخلات: **`What is the minlength attribute?`**.

*ملاحظة سريعة:* تجاوزنا السؤال الثالث (والذي غالبًا ما يكون السمة التوأم `max` أو `maxlength` حسب ترتيبك) لندخل مباشرة في تفاصيل الـ `minlength` بناءً على طلبك.

تعال نفصص الـ `minlength attribute` بأعلى عمق هندسي وأسهل أسلوب.

## 1. التشبيه العبقري (بوابة فحص الحقائب في الطيران العارض)

تخيل أنك مسافر على خطوط طيران اقتصادية، ولديهم شرط صارم لضمان استقرار الطائرة: "ممنوع شحن أي حقيبة يقل وزنها عن 8 كيلوغرامات" (هذا هو الـ **`minlength="8"`**).
إذا جئت بحقيبة صغيرة جداً وزنها 5 كيلو فقط، سيوقفك موظف الفحص ويقول لك: "عذراً، حقيبتك خفيفة جداً، يجب أن تضيف إليها بعض الأشياء لتصل للحد الأدنى المسموح به قبل أن نسمح لها بالصعود إلى الطائرة!".

الـ `minlength` هو هذا الميزان؛ يرفض المتصفح استقبال أو إرسال أي نص ما لم يستوفِ الحد الأدنى من عدد الحروف المطلوبة.

## 2. السلوك الفني والبرمجي (من كودك الممتاز)

في مثالك الرائع المخصص لـحماية الحسابات:

HTML

```
<input type="password" minlength="8">
```

بمجرد إضافة هذه السمة مع الـ `type="password"` (أو حتى مع الـ `type="text"` والـ `textarea`):

1. **التحقق اللحظي قبل الإرسال (Constraint Validation):** إذا حاول المستخدم كتابة كلمة مرور قصيرة وسهلة التخمين تتكون من 5 حروف فقط (مثل `12345`) وضغط على Submit، المتصفح سيتدخل فوراً، ويمنع إرسال الفورم، ويظهر رسالة خطأ صريحة: *"Please lengthen this text to 8 characters or more (you are currently using 5 characters)."*
2. **عدم إزعاج المستخدم أثناء الكتابة (Smart UX):** من مميزات المتصفح الذكية أنه **لا يظهر** رسالة الخطأ للمستخدم أثناء كتابته للحروف الأولى؛ بل ينتظر حتى يحاول المستخدم الضغط على زر الإرسال (Submit) أو ينقل التركيز خارج الحقل (Blur)، لكي لا يسبب له الإزعاج أثناء الكتابة.

## 3. الفرق الهندسي الحاسم: `min` ضد `minlength` (تريكة المقابلات!)

قد يختبر المقابل دقة ملاحظتك ويسألك: **"ما الفرق بين min و minlength؟"**

- **`min`:** تُستخدم لتقييد **القيمة العددية أو الزمنية** (Value)، وتعمل مع `type="number"` و `type="date"`. (مثال: السن لا يقل عن `18`).
- **`minlength`:** تُستخدم لتقييد **عدد الحروف (عدد الرموز - Character Count)** في النص، وتعمل مع الـ `text`, `password`, `email`, والـ `textarea`. (مثال: كلمة المرور لا تقل عن `8` حروف بغض النظر عن محتواها).

## الكلمات المفتاحية للحفظ (Keywords)

- **`Character Count Constraint`:** تقييد عدد الحروف المدخلة.
- **`Constraint Validation API`:** واجهة المتصفح البرمجية للتحقق من القيود.
- **`Password Security Enforcement`:** فرض معايير أمان كلمات المرور في الواجهة الأمامية.
- **`Min vs. Minlength`:** التفرقة بين حجم القيمة الرياضية وعدد المحارف النصية.

> **جملتك النموذجية في المقابلة:**
"The **`minlength` attribute** is a native HTML5 validation attribute that defines the minimum number of characters a user can enter into a text, password, or textarea field. In the example **`minlength="8"`**, the browser will automatically block form submission if the password is shorter than 8 characters, displaying a native tooltip helper. It is highly beneficial for **security enforcement** in login and registration forms, as it provides a lightweight, zero-JS way to ensure users create stronger passwords before any data is sent to the server
>

تعال نفصص الـ `maxlength attribute` بأعلى عمق هندسي وبأسهل أسلوب.

## 1. التشبيه العبقري (صندوق البريد الحديدي الصغير)

تخيل أن لديك صندوق بريد حديدياً معلقاً على باب بيتك، وفتحة الصندوق مصممة لكي تتسع لـ 20 رسالة كحد أقصى (هذا هو الـ **`maxlength="20"`**).

إذا جاء ساعي البريد ومعه 20 رسالة، سيدخلون بالكامل. لكن، إذا حاول دفع الرسالة رقم 21 داخل الفتحة، فلن تدخل ميكانيكياً لأن الصندوق امتد لامتلائه تماماً ولم تعد هناك مساحة لحرف واحد إضافي! لن ينتظر الصندوق حتى تنتهي، بل سيمنعه في نفس اللحظة.

الـ `maxlength` هو هذا الجدار الحديدي الصارم؛ إنه يمنع أصابع المستخدم من كتابة أي حرف زائد عن الحد.

## 2. السلوك الفني والبرمجي الفريد (من كودك الممتاز)

في مثالك الواضح والمباشر:

HTML

```
<input type="text" maxlength="20">
```

بمجرد إضافة هذه السمة، يتغير سلوك الحقل في المتصفح كالتالي:

1. **المنع الفيزيائي الفوري (Hard Ceiling):** على عكس بقية السمات (مثل `minlength` أو `required`) التي تنتظر حتى يضغط المستخدم على Submit لتعترض؛ الـ `maxlength` **تمنع المستخدم من الكتابة فوراً في نفس اللحظة**! إذا وصل المستخدم للحرف رقم 20 وحاول الضغط على لوحة المفاتيح لكتابة الحرف رقم 21، فلن يظهر الحرف على الشاشة ولن يستجيب الحقل نهائياً كأنه معطل.
2. **غياب رسائل الخطأ (No Error Tooltips):** بما أن المتصفح منع المستخدم من ارتكاب الخطأ أصلاً ولم يترك له فرصة لكتابة حرف زائد، فلن تظهر أي رسالة خطأ (Tooltip) عند الضغط على زر الـ Submit؛ لأن المدخلات دائمًا ستكون سليمة وضمن الحدود ($\le 20$ حرف).

## 3. لماذا نستخدم الـ `maxlength` في المشاريع الحقيقية؟

بصفتك مهندس واجهات (UI Engineer) محترف، اذكر للمقابل أهم الحالات العملية لاستخدامها:

- **مطابقة حدود قواعد البيانات (Database Constraints):** إذا كان مهندس الباكيند قد صمم جدول قاعدة البيانات بحيث يتسع حقل "الاسم المستعار (Username)" لـ 20 حرفاً فقط كحد أقصى (مثلاً `VARCHAR(20)`)؛ فإن وضعك لـ `maxlength="20"` في الـ HTML يضمن عدم حدوث خطأ في الخادم (Database Crash / Truncation Error) بسبب محاولة إرسال نص أطول مما تتحمله قاعدة البيانات.
- **الحقول ذات الأطوال الثابتة القياسية:** مثل كتابة الرقم القومي، أرقام بطاقات الائتمان (16 حرفاً)، أو الرموز البريدية لمنع كتابة أرقام عشوائية زائدة بالخطأ.

## 💡 تريكة المحترفين لـ تجربة مستخدم فائقة (Advanced UX)

بما أن المتصفح يتوقف عن الكتابة فجأة دون تحذير، قد يظن المستخدم أن لوحة مفاتيحه قد تعطلت!

لذلك، في الواجهات الاحترافية، ندمج الـ `maxlength` مع سكريبت جافاسكريبت بسيط يعرض عداداً تنازلياً للمستخدم (Character Counter) يوضح له كم حرفاً متبقياً له (مثل: "متبقي لك 5 حروف من أصل 20")؛ لتنبيهه قبل الوصول للجدار الصارم.

## الكلمات المفتاحية للحفظ (Keywords)

- **`Hard Ceiling Constraint`:** سقف برمي صارم يمنع إدخال المزيد من المحارف.
- **`Database Alignment (VARCHAR)`**: مطابقة القيود مع المساحة التخزينية لقواعد البيانات.
- **`Character Counter UX`**: عداد الحروف المتبقية لتحسين تجربة المستخدم.
- **`Instant Keypress Blocking`**: حجب استجابة لوحة المفاتيح فور تجاوز الحد.

> **جملتك النموذجية في المقابلة:**
> 
> 
> "The **`maxlength` attribute** sets a strict physical limit on the maximum number of characters a user can enter into a text field or textarea. In the example **`maxlength="20"`**, the browser enforces a **hard ceiling** by instantly blocking any further keypresses once the 20-character limit is reached. Unlike other validation attributes, it doesn't show an error tooltip upon submission because it prevents the error from happening in the first place. It is crucial for aligning frontend forms with **database constraints** (like a `VARCHAR(20)` limit) to avoid server-side insertion errors
> 

## Senior Notes

`maxlength` يمنع المستخدم من إدخال أحرف إضافية في معظم المتصفحات، بينما `minlength` يعتمد على التحقق عند إرسال النموذج.

# الشرح بالتفصيل

وصلنا للسؤال السادس في قسم **`4.3 Input Attributes (Part 2)`**، وهي السمة التي تمنح المستخدمين حرية الاختيار المتعدد بضغطة زر واحدة: **`What is the multiple attribute?`**.

في المقابلات الشخصية، الـ Interviewer بيطرح السؤال ده عشان يتأكد إنك فاهم إزاي بتمكن المستخدم من رفع ملفات متعددة أو اختيار أكتر من عنصر، وإزاي المتصفح بيتعامل مع حزم البيانات دي وقت الإرسال.

تعال نفصص الـ `multiple attribute` بأعلى عمق هندسي وأسهل أسلوب.

## 1. التشبيه العبقري (سلة التسوق الكبيرة ضد عربة الشراء)

تخيل لو أنت داخل سوبرماركت، وفي يدك "علبة صغيرة" لا تتسع إلا لمنتج واحد فقط. كل ما تختار منتج تضطر تروح تدفع تمنه وترجع تاني عشان تختار غيره.
لكن لو السوبرماركت وفر لك **"عربة تسوق ضخمة"** (دي صفة الـ **`multiple`**)، تقدر بضغطة واحدة تمسك 3 أو 4 منتجات وتحطهم مع بعض في العربة وتشحنهم كلهم للكاشير (السيرفر) في خطوة واحدة!

الـ `multiple` بتحول الحقل من حقل أحادي الاختيار إلى عربة تتسع لخيارات متعددة في نفس الوقت.

## 2. السلوك الفني والبرمجي (من كودك الممتاز)

في مثالك الرائع والعملي جداً لرفع الملفات:

HTML

```
<input type="file" multiple>
```

بمجرد إضافة السمة البولية `multiple` (واللي بتتفعل بمجرد كتابتها كدة):

1. **تغيير واجهة اختيار الملفات (File Picker UI):** لما المستخدم يضغط على الزرار، نظام التشغيل (ويندوز، ماك، أو موبايل) بيسمح له إنه يضغط على زرار `Ctrl` أو `Shift` ويحدد **أكثر من ملف في نفس الوقت** (مثلاً: يرفع 5 صور معاً). بدون الـ `multiple` لو حاول يختار صورة تانية، المتصفح بيمسح الصورة الأولى تلقائياً.
2. **شكل البيانات خلف الكواليس (FileList Object):** في الجافاسكريبت، الحقل ده مش بيحتوي على ملف واحد، بل بيتحول لكائن مصفوفي اسمه `FileList` بيحتوي على كل الملفات اللي تم اختيارها بترتيب رقمي (`files[0]`, `files[1]`).

## 3. الدمج السحري: الـ `multiple` مع الـ `<select>` والـ `type="email"`

المقابل الذكي ممكن يسألك: **"هل الـ multiple بتشتغل مع الـ file input بس؟"**
وهنا لازم تبهر بالإجابة دي وتوضح إن ليها استخدامين تانين مشهورين جداً:

- **مع الـ `<select>` (القوائم المنسدلة):**HTML
    
    ```
    <select multiple>
    ```
    
    *(هنا القائمة المنسدلة بتتحول لصندوق مفتوح، ويقدر المستخدم يختار أكتر من عنصر - مثل اختيار عدة مهارات أو دول - بالضغط على Ctrl أو Cmd أثناء الاختيار).*
    
- **مع الـ `type="email"` (البريد الإلكتروني):**HTML
    
    ```
    <input type="email" multiple>
    ```
    
    *(هنا المتصفح بيسمح للمستحدم بكتابة أكثر من بريد إلكتروني داخل نفس الخانة بشرط الفصل بينهم بـ **فاصلة `,`**، وبيعمل تحقق تلقائي للتأكد إن كل الإيميلات المكتوبة صيغتها سليمة!).*
    

## الكلمات المفتاحية للحفظ (Keywords)

- **`Multi-selection UI`:** واجهة تسمح بالاختيار المتعدد.
- **`FileList Object`:** مصفوفة الملفات المخزنة في الجافاسكريبت عند الرفع.
- **`Comma-separated values`:** القيم المفصولة بفاصلة (في حالة الـ email).
- **`Boolean Attribute`:** سمة منطقية يكفي كتابة اسمها لتفعيلها.

> **جملتك النموذجية في المقابلة:**
"The **`multiple` attribute** is a boolean attribute that allows the user to enter or select more than one value in a single input control. In the example **`<input type="file" multiple>`**, it triggers the native OS file picker to allow selecting multiple files simultaneously, which are stored as a **`FileList` object** in JavaScript. Beyond file inputs, the `multiple` attribute can also be used with **`<select>` elements** for multi-option lists, and with **`type="email"`** to allow users to input a comma-separated list of valid email addresses
>

# الشرح بالتفصيل

وصلنا للسؤال السابع  في هذه المجموعة من قسم **`4.3 Input Attributes (Part 2)`**، وهي السمة الحارسة لنوعية الملفات المرفوعة: **`What is the accept attribute?`**.

في المقابلات الشخصية، يحب الـ Interviewer اختبار مدى فهمك لتجربة رفع الملفات (File Upload UX) والأمان الأساسي للواجهات باستخدام الـ `accept` لتصفية خيارات المستخدم.

تعال نفصص الـ `accept attribute` ونفهم كيف تعمل خلف الكواليس وبداخل نظام التشغيل.

## 1. التشبيه العبقري (حارس البوابة ذو الفلتر الذكي)

تخيل لو أنك تقيم حفلة تنكرية والشرط الوحيد للدخول هو ارتداء "قناع أبيض". لكي تضمن التزام الجميع، وضعت حارساً عند البوابة الخارجية (هذا هو الـ **`accept`**).

عندما يقترب الضيوف من الباب، يقوم الحارس تلقائياً بوضع علامة "مرئي" فقط على الأشخاص الذين يرتدون الأقنعة البيضاء، بينما يجعل الآخرين غير مرئيين أو يمنعهم من الوقوف في الطابور أصلاً.

هذا ما تفعله سمة `accept`؛ إنها تُخبر نافذة نظام التشغيل ألا تَعرض للمستخدم إلا الملفات المتوافقة مع الصيغة المحددة وتُخفي أو تُعطل اختيار الملفات الأخرى.

## 2. السلوك الفني والبرمجي (من كودك الممتاز)

المتصفح يتعامل مع الـ `accept` بطريقتين ذكيتين بناءً على المدخلات المكتوبة:

### الطريقة الأولى: التصفية بالامتداد المباشر (File Extension)

HTML

```
<input type="text" type="file" accept=".pdf">
```

- **السلوك:** عندما يضغط المستخدم على الزر، تفتح نافذة اختيار الملفات (File Explorer أو Finder) وتكون مجهزة بـ "فلتر" تلقائي لا يعرض سوى الملفات التي تنتهي بامتداد `.pdf`. باقي الملفات (مثل الصور أو ملفات الـ Word) ستظهر باهتة (Disabled) ولا يمكن تحديدها.

### الطريقة الثانية: التصفية بنوع الـ MIME (MIME Type Wildcards)

HTML

```
<input type="file" accept="image/*">
```

- **السلوك:** هنا نستخدم الـ MIME types مع الرمز العام  (Wildcard). هذا يعني قبول أي نوع من أنواع الصور (سواء كانت `.png`, `.jpg`, `.gif`, `.webp` إلخ). المتصفح يفهم هذه المجموعات القياسية تلقائياً:
    - `image/*`: أي ملف صورة.
    - `audio/*`: أي ملف صوتي (مثل `.mp3`, `.wav`).
    - `video/*`: أي ملف فيديو (مثل `.mp4`, `.mov`).
    - `application/pdf`: ملفات PDF تحديداً (وهي التسمية الرسمية للـ MIME type الخاص بها).

## 3. تحذير أمني خطير للمقابلات الشخصية (Security Warning) ⚠️

هذه أهم نقطة تضمن لك تخطي أي سؤال أمان في المقابلات:

> **"الـ `accept` هي أداة لتحسين تجربة المستخدم (UX Improvement) وليست أداة أمان برمجية (Security Validation)."**
> 

لماذا؟ لأن المستخدم المحترف يستطيع بسهولة الالتفاف حول هذا القيد وتغيير إعداد الفلتر داخل نافذة نظام التشغيل واختيار ملف من نوع آخر (مثل اختيار ملف `.exe` ضار وتسميته `.png` أو تجاوزه عبر أدوات المطورين).

لذلك، يجب عليك دائماً إخبار المقابل بالآتي:

> "نحن نستخدم `accept` في الواجهة الأمامية كخطوة أولى لتسهيل الاختيار على المستخدم، ولكن **يجب دائماً** التحقق من صيغة ونوع الملفات المرفوعة في الخلفية (Backend validation) لضمان أمن الخادم."
> 

## الكلمات المفتاحية للحفظ (Keywords)

- **`File Filtering (OS level)`**: تصفية الملفات على مستوى نظام التشغيل.
- **`MIME Type Wildcards`**: استخدام الرمز العام (مثل `image/*`) لتصفية مجموعات الملفات كاملة.
- **`UX Helper, Not a Security Guard`**: ميزة لتحسين تجربة المستخدم وليست حماية أمنية نهائية.
- **`Backend Validation Required`**: ضرورة الفحص في السيرفر لمنع الثغرات الأمنية.

> **جملتك النموذجية في المقابلة:**
> 
> 
> "The **`accept` attribute** is used to filter and restrict the types of files a user can upload. In the example **`accept="image/*"`**, the browser instructs the OS file picker to only display and allow selection of image files. While it accepts file extensions like **`.pdf`** or MIME types like **`audio/*`**, it is critical to remember that `accept` is a **UX enhancement tool**, not a security feature. Users can easily bypass client-side filters, so **backend validation** of the uploaded file's type and content is mandatory for system security
>

# الشرح بالتفصيل

صلنا للسؤال الثامن في قسم **`4.3 Input Attributes (Part 2)`**، وهو السمة السحرية المخصصة للهواتف الذكية والأجهزة المحمولة: **`What is the capture attribute?`**.

في المقابلات الشخصية، هذا السؤال هو المفضل لدى الـ Interviewers عند الحديث عن الـ **Mobile UX (تجربة المستخدم على الهواتف)** والـ **PWA (تطبيقات الويب التقدمية - Progressive Web Apps)**، لأنه يختبر مدى قدرتك على دمج ميزات الهاتف الأصلية (Native Mobile Features) داخل متصفح الويب مباشرة دون الحاجة لبناء تطبيق موبايل كامل (Native App).

تعال نفصص الـ `capture attribute` بأعلى عمق هندسي وبأسهل أسلوب.

## 1. التشبيه العبقري (زر الاختصار المباشر للكاميرا)

تخيل لو أنك واقف في طابور لتسجيل الدخول في فندق، وموظف الاستقبال قال لك: "أريد صورة من بطاقتك الشخصية".

- **الطريقة التقليدية الصعبة:** تفتح تطبيق الكاميرا على موبايلك، وتلتقط الصورة، ثم تفتح المتصفح، وتضغط على "رفع ملف"، وتبحث في معرض الصور (Gallery) المزدحم بآلاف الصور حتى تجد الصورة التي التقطتها للتو وترفعها.
- **طريقة الـ `capture` السحرية:** تضغط على زر "رفع الصورة" في الموقع، **فتفتح الكاميرا فوراً وبشكل تلقائي**، تلتقط الصورة، وبمجرد الضغط على علامة صح (✓) يتم رفعها للموقع مباشرة في ثانية واحدة!

الـ `capture` هو هذا الاختصار والممر المباشر لكاميرا الهاتف أو الميكروفون.

## 2. السلوك الفني والبرمجي وقيم السمة (من كودك الممتاز)

في مثالك الاحترافي:

HTML

```
<input type="file" accept="image/*" capture="environment">
```

بمجرد دمج الـ `capture` مع الـ `type="file"` وتحديد نوع الملفات المقبولة (مثل `accept="image/*"` أو `accept="video/*"`):

1. **الوصول المباشر للعتاد (Hardware Access):** بدلاً من فتح ملفات الجهاز (File Explorer / Gallery)، المتصفح يقوم باستدعاء كاميرا الهاتف أو جهاز تسجيل الصوت مباشرة.
2. **التحكم في اتجاه الكاميرا (Camera Facing):** نتحكم في الكاميرا التي تفتح تلقائياً للمستخدم عبر قيمتين أساسيتين:

### أ. القيمة الأولى: `capture="user"`

- **الشرح:** تعني الكاميرا المواجهة للمستخدم مباشرة (الكاميرا الأمامية - Front Camera).
- **أشهر استخدام:** التقاط صور السيلفي (Selfies)، عمليات التحقق من الهوية بالوجه (Face Recognition / KYC)، أو تسجيل فيديو سريع للمستخدم.

### ب. القيمة الثانية: `capture="environment"`

- **الشرح:** تعني الكاميرا المواجهة للبيئة المحيطة (الكاميرا الخلفية - Rear Camera).
- **أشهر استخدام:** تصوير المستندات والبطاقات (Document Scanning)، تصوير الباركود (QR Codes)، أو التقاط صور للمناظر الطبيعية والمنتجات.

## 3. سلوك السمة على أجهزة الكمبيوتر (Desktop Behavior)

سؤال فخ ذكي جداً في المقابلات: **"ماذا يحدث لو فتح المستخدم الموقع من جهاز كمبيوتر مكتبي (Desktop) لا يحتوي على كاميرا خلفية أو لمسية، وحاول الضغط على الـ input هذا؟"**

- **الإجابة الهندسية:** المتصفح يتمتع بمرونة عالية تسمى الـ **Graceful Degradation** (التراجع الأنيق)؛ حيث يتجاهل المتصفح سمة `capture` تماماً ويتصرف كأنه حقل رفع ملفات عادي جدًا (`<input type="file">`) فيفتح للمستخدم نافذة اختيار الملفات العادية ليختار منها ملفاً مخزناً مسبقاً على جهازه دون أن يتعطل الموقع أو يتوقف عن العمل.

## الكلمات المفتاحية للحفظ (Keywords)

- **`Native Device Hardware Access`**: الوصول المباشر لعتاد الجهاز الأصلي (الكاميرا/الميكروفون).
- **`Front Camera (user)`**: الكاميرا الأمامية الموجهة للمستخدم.
- **`Rear Camera (environment)`**: الكاميرا الخلفية الموجهة للبيئة المحيطة.

What is the value attribute?   المثال

<input

type="text"

وصلنا للسؤال التاسع في قسم **`4.3 Input Attributes (Part 2)`**، وهو السمة المركزية لـ "جوهر" البيانات وعمودها الفقري: **`What is the value attribute?`**.

في المقابلات الشخصية، السؤال ده ممكن يبان بديهي جداً، لكن الـ Interviewer بيستغله كمدخل لأسئلة أعمق بكتير في الـ JavaScript حول الفرق بين الـ **Attribute** والـ **Property**، وإزاي الـ Forms بتتعامل مع البيانات وقت الإرسال أو عند عمل Reset.

تعال نفصص الـ `value attribute` بأعلى عمق هندسي وبأسهل أسلوب.

## 1. التشبيه العبقري (صندوق الأمانات المحجوز مسبقاً)

تخيل لو دخلت فندق، وموظف الاستقبال سلمك مفتاح صندوق الأمانات الخاص بغرفتك، ولما فتحت الصندوق لقيت الإدارة حاطة لك جواه "هدية ترحيبية عبارة عن ساعة يد قيمتها مكتوبة عليها" (دي الـ **`value="Hanan Awad"`**).
الساعة دي موجودة جوة الصندوق من اللحظة الأولى؛ تقدر تسيبها زي ما هي، وتقدر تشيلها وتحط مكانها حاجة تخصك أنت، وتجربة الفندق بدأت وهي موجودة بالفعل.

الـ `value` في الـ HTML هي القيمة الابتدائية الجاهزة اللي بتملى الصندوق (الـ input) من أول ما الصفحة تفتح وقبل ما المستخدم يلمس لوحة المفاتيح.

## 2. السلوك الفني والبرمجي (من كودك الممتاز)

في مثالك الواضح والنظيف:

HTML

```
<input type="text" value="Hanan Awad">
```

بمجرد استخدام السمة دي، بيحصل الآتي:

1. **القيمة الافتراضية (Default/Initial Value):** المتصفح بمجرد ما يرسم الصفحة (DOM Rendering)، هيملى الخانة دي بنص `"Hanan Awad"` تلقائياً بدل ما يسيبها فاضية.
2. **شحنة البيانات (Form Payload):** لو المستخدم ساب الخانة زي ما هي وضغط على Submit، المتصفح هياخد النص ده (`Hanan Awad`) ويبعته فوراً للسيرفر كقيمة للحقل ده.

## 3. السر الهندسي الأهم للمقابلات: الـ Attribute ضد الـ Property (فخ الجافاسكريبت!)

المقابل هنا هيسألك سؤال ذكي جداً: **"لو المستخدم مسح كلمة 'Hanan Awad' وكتب مكانها 'Ali'، ودخلنا بالجافاسكريبت نقرأ الحقل.. إيه اللي هيحصل؟"**
وهنا لازم تظهر قوتك وتفرق بين حاجتين:

- **الـ HTML Attribute (السمة في الكود):** ودي بتفضل دايماً محتفظة بالقيم الأصلية الثابتة في الـ HTML (تسمى الـ `defaultValue`). حتى لو المستخدم غير الكلام، الـ Attribute بيفضل شايل `"Hanan Awاد"`. وعشان كدة لو عملنا `form.reset()` الحقل بيرجع للكلمة دي!
- **الـ JavaScript Property (الحالة الحالية في الـ DOM):** دي بتمثل اللي مكتوب قدام عيون المستخدم "حالياً" في الشاشة (`input.value`). بمجرد ما المستخدم يكتب `Ali`، الـ Property بتتحدث فوراً وبتكون قيمتها الحالية `"Ali"`.

## 4. كيف تختلف الـ `value` حسب الـ `type`؟

المحترفون يعرفون أن سلوك الـ `value` يتغير جذرياً حسب نوع الحقل:

- **مع الـ `text`, `email`, `password`:** بتمثل النص المكتوب داخل الخانة.
- **مع الـ `button`, `submit`:** بتمثل النص (اللافتة) المكتوبة فوق الزرار (مثل `value="Register Now"`).
- **مع الـ `checkbox`, `radio`:** (تريكة خطيرة!) القيمة مش بتظهر للمستخدم على الشاشة، لكنها القيمة المخفية اللي هتروح للسيرفر **فقط لو** المستخدم حدد (Checked) الاختيار ده!

## الكلمات المفتاحية للحفظ (Keywords)

- **`Initial / Default Value`:** القيمة الابتدائية الافتراضية عند تحميل الصفحة.
- **`HTML Attribute vs. DOM Property`:** الفرق بين السمة الأصلية في الكود والحالة الديناميكية الحالية.
- **`Form Payload Submission`:** القيمة التي يتم شحنها وإرسالها إلى السيرفر.
- **`The defaultValue Object`:** كائن الجافاسكريبت الذي يحتفظ بالقيمة الأصلية لعمل الـ Reset.

> **جملتك النموذجية في المقابلة:**
"The **`value` attribute** specifies the initial or default value contained within an input field when the page loads. In the example **`value="Hanan Awad"`**, it pre-populates the input text. Architecturally, we must distinguish between the **HTML attribute** (which defines the structural `defaultValue` used during a form reset) and the **DOM property** (which tracks the dynamic, real-time value typed by the user via JavaScript `input.value`). Furthermore, its behavior changes based on the input type; for text fields it represents the textual data, while for checkboxes or radio buttons, it represents the hidden data payload submitted to the server only if the element is checked
>

في المقابلات الشخصية، هذا السؤال يقيس مدى اهتمامك بالـ **Accessibility (إتاحة الوصول)** والـ **Conversion Rate Optimization (تحسين معدلات التحويل)**؛ لأن تقليل النقرات (Clicks) التي يقوم بها المستخدم للبدء في استخدام موقعك هو علامة فارقة بين التصميم العادي والتصميم الاحترافي.

تعال نفصص الـ `autofocus attribute` بأعلى عمق هندسي وبأسهل أسلوب.

## 1. التشبيه العبقري (الموظف الذي يفتح لك الباب ويمد لك القلم)

تخيل لو أنك دخلت بنكاً لتحديث بياناتك، وبمجرد دخولك من الباب، لم تجد نفسك مضطراً للبحث عن مكان القلم أو الخانة التي يجب أن تكتب فيها؛ بل وجدت موظفاً يستقبلك بابتسامة، ويسحب لك الكرسي، ويضع القلم في يدك مباشرة فوق خانة "البريد الإلكتروني" ويقول لك: "تفضل بالكتابة فوراً". أنت لم تبذل أي مجهود في البحث أو التوجيه.

الـ `autofocus` هو هذا الموظف؛ فهو يضع مؤشر الكتابة (Cursor) داخل الخانة تلقائياً بمجرد فتح الصفحة، ليكون المستخدم جاهزاً للكتابة دون الحاجة للضغط بالماوس على الخانة.

## 2. السلوك الفني والبرمجي (من كودك الممتاز)

في مثالك النظيف والمباشر:

HTML

```
<input type="email" autofocus>
```

الـ `autofocus` هي سِمَة ثنائية (Boolean Attribute) — أي أن مجرد وجودها في العنصر يعني أنها مفعّلة (True). وبمجرد تحميل الصفحة (Page Load)، يحدث الآتي تكنولوجياً:

1. **تركيز الـ DOM الفوري (Immediate DOM Focus):** يقوم المتصفح تلقائياً بنقل التركيز النشط (Active Focus) إلى هذا الحقل بالذات دون انتظار أي نقرة من المستخدم.
2. **استدعاء لوحة المفاتيح (Soft Keyboard Trigger):** على الهواتف الذكية (iOS / Android)، وجود هذه السمة قد يتسبب في فتح لوحة المفاتيح الافتراضية فوراً ليكون المستخدم مستعداً للكتابة (حسب إعدادات نظام التشغيل والمتصفح).

## 3. القواعد والمحاذير الهندسية (أسرار المقابلات الشخصية 💡)

هنا سيسألك الـ Interviewer فخاً هندسياً: **"ماذا يحدث لو وضعت سمة `autofocus` على أكثر من حقل في نفس الصفحة؟"**

- **الإجابة الهندسية:** القاعدة الصارمة في الـ HTML هي: **"يُسمح بعنصر واحد فقط يحمل سمة `autofocus` في كل وثيقة HTML"**. إذا قمت بوضعها على أكثر من حقل، فإن المتصفح سيقوم بالتركيز على **أول حقل** يقرأه في الـ DOM ويتجاهل الباقي (وفي بعض المتصفحات القديمة قد ينتقل لآخر حقل)، لذا يعتبر وضعها على أكثر من عنصر خطأ برمجي (Bad Practice).
- **تحذير الـ Accessibility (إمكانية الوصول):** يجب استخدامها بحذر شديد! للمستخدمين الذين يعتمدون على قارئات الشاشة (Screen Readers) أو مستخدمي لوحة المفاتيح فقط (Keyboard-only users)، قد يسبب الـ `autofocus` إرباكاً؛ لأنه ينقلهم فجأة لمنتصف الصفحة أو لخانة معينة دون أن يقرأوا مقدمة الصفحة أو العناوين الرئيسية، لذا يُفضل استخدامها فقط في الصفحات المخصصة لغرض واحد واضح (مثل صفحة تسجيل الدخول `Login` أو صفحة البحث مثل `Google`).

## الكلمات المفتاحية للحفظ (Keywords)

- **`Boolean Attribute`**: سمة ثنائية (تُفعل بمجرد كتابة اسمها).
- **`Initial Focus / Active Element`**: تركيز المتصفح الفوري وجعل العنصر هو النشط عند تحميل الصفحة.
- **`One per Document Rule`**: قاعدة استخدام عنصر واحد فقط لكل صفحة.
- **`User Experience (UX) Optimization`**: تحسين تجربة المستخدم وتقليل الاحتكاك (Friction).

In the example, it targets the `email` field, which is excellent for dedicated pages like a login or registration screen. Globally, architectural rules dictate that **only one element per document** can have the `autofocus` attribute. Additionally, from an **Accessibility (a11y)** standpoint, it should be used carefully, as warping the focus automatically can sometimes disorient users who rely on screen readers or keyboard navigation

# السؤال الأول

# What happens when a form is submitted?

---

## الشرح بالتفصيل

دخلنا رسميًا في القسم **`4.4 Form Submission`**، وهو المحطة التي تتحول فيها واجهة المستخدم الرسومية إلى بروتوكول شبكة حقيقي! سؤالك الأول هو أحد أكثر أسئلة المقابلات كلاسيكية وعمقًا: **`What happens when a form is submitted?`**.

هذا السؤال لا يقيس معرفتك بالـ HTML فحسب، بل يختبر فهمك لكيفية عمل الويب خلف الكواليس، وبنية بروتوكول HTTP، وكيفية انتقال البيانات عبر الشبكة (Network Layers).

تعال نفصص عملية الـ Form Submission بأعلى عمق هندسي وأسهل أسلوب.

## 1. التشبيه العبقري (مكتب البريد وشاحنة الشحن)

تخيل أن الـ Form عبارة عن استمارة ورقية ملأتها ببياناتك، ووضعتها داخل صندوق كرتوني صغير.
بمجرد أن تضغط على زر **"إرسال (Submit)"**:

1. يأتي موظف المتصفح، ويغلق الصندوق بشريط لاصق، ويكتب عليه من الخارج عنوان المستلم (السيرفر) وطريقة الشحن.
2. يضع الصندوق داخل شاحنة نقل (طلب الـ HTTP).
3. تتحرك الشاحنة عبر الطريق (الإنترنت) وتصل إلى باب المصنع (السيرفر).
4. المصنع يفتح الصندوق، يقرأ الاستمارة، يفرز البيانات، ثم يرسل لك رسالة تأكيد (مثل: "تم التسجيل بنجاح").

## 2. الدورة التقنية المفصلة (The Technical Lifecycle)

عندما يضغط المستخدم على زر الـ Submit، يمر المتصفح بـ **4 خطوات متتالية وصارمة**:

### الخطوة الأولى: التثبت والتحقق (Form Validation)

قبل أن يرسل المتصفح أي شيء عبر الشبكة، يقوم بعمل فحص داخلي أولي (Client-side Validation). يتأكد من أن كل الحقول تلتزم بالقيود التي درسناها سابقاً (مثل `required`, `pattern`, `minlength`).

- إذا وجد خطأ 👈 يتوقف الإرسال فوراً (Form Submission Canceled) ويظهر تنبيه للمستخدم.
- إذا كانت البيانات سليمة 👈 ينتقل للخطوة التالية.

### الخطوة الثانية: تجميع البيانات وترميزها (Data Encoding)

المتصفح يمر على كل حقول الإدخال (`<input>`, `<textarea>`, `<select>`) داخل الـ `<form>` ويجمع البيانات.

> ⚠️ **شرط حرج للمقابلات:** المتصفح سيتجاهل تماماً أي حقل لا يحتوي على سمة **`name`**! سمة الـ `name` هي بمثابة المفتاح (Key) والـ value هي القيمة.
> 

يقوم المتصفح بتحويل هذه الثنائيات لنمط نصي مشفر (عادة يكون `application/x-www-form-urlencoded`)، ليصبح شكل البيانات هكذا:

Plaintext

```
username=Hanan+Awad&email=hanan%40example.com
```

### الخطوة الثالثة: بناء وإرسال طلب الـ HTTP (HTTP Request)

يقوم المتصفح بإنشاء طلب ويب رسمي مستخدماً صفتين رئيسيتين في عنصر الـ `<form>`:

1. **`action`**: تحدد الرابط (URL) أو الوجهة التي ستذهب إليها الشاحنة (مثال: `/api/login`).
2. **`method`**: تحدد نوع الطلب، وإليك ما يحدث للبيانات بناءً عليها:
    - **`GET`**: يأخذ المتصفح البيانات المرمزة ويلصقها مباشرة في نهاية رابط الموقع (URL) بعد علامة استفهام تسمى (Query String)، هكذا: `mysite.com/login?username=Hanan`.
    - **`POST`**: يضع المتصفح البيانات سراً ومحمية داخل جسم الطلب (HTTP Request Body)، وهي الطريقة الآمنة والمستخدمة لبيانات الحسابات والملفات.

### الخطوة الرابعة: انتظار الرد وتحديث الصفحة (The HTTP Response)

يصل الطلب للسيرفر، فيقوم بمعالجتها (مثلاً التحقق من كلمة المرور في قاعدة البيانات)، ثم يرد السيرفر على المتصفح بـ **HTTP Response** (مثل كود النجاح `200 OK` أو إعادة التوجيه `302 Redirect`).
تلقائياً، **يقوم المتصفح بإعادة تحميل الصفحة (Page Refresh)** لعرض الرد الجديد القادم من السيرفر، ما لم نقم بإيقاف هذا السلوك عبر الجافاسكريبت باستخدام `e.preventDefault()`.

## الكلمات المفتاحية للحفظ (Keywords)

- **`Constraint Validation Check`**: فحص قيود البيانات قبل الإرسال.
- **`Name Attribute Requirement`**: إلزامية وجود سمة name لتجميع البيانات.
- **`Form Encoding (URL-Encoded / Multipart)`**: ترميز وتشفير بيانات النموذج.
- **`Query String (GET Method)`**: سلسلة البيانات الملحقة بالرابط في طلبات GET.
- **`Request Body (POST Method)`**: جسم الطلب الحاضن للبيانات في طلبات POST.
- **`Full Page Refresh`**: إعادة تحميل الصفحة الكاملة افتراضياً بعد الرد.

> **جملتك النموذجية في المقابلة:**
"When a form is submitted, the browser initiates a 4-step lifecycle. First, it performs native **client-side validation**. Second, it harvests data from all fields that possess a **`name` attribute** and encodes them. Third, based on the form's **`method`**, it constructs an HTTP Request: if it's a **GET**, data is appended to the URL as a **query string**; if it's a **POST**, data is encapsulated securely inside the **HTTP Request Body**, and sent to the endpoint specified in the **`action` attribute**. Finally, once the server processes the data and responds, the browser by default triggers a **full page refresh** to render the new server response, unless intercepted by JavaScript via `e.preventDefault()`."
>

> **Successful Controls**

# السؤال الثاني

# What is the difference between GET and POST?

## الشرح بالتفصيل

وصلنا للسؤال الثاني، وهو السؤال الأكثر شهرة وتكراراً في مقابلات توظيف مطوري الويب على الإطلاق: **`What is the difference between GET and POST?`**.

هذا السؤال لا يختبر الـ HTML فقط، بل يغوص في عمق **بروتوكول الويب (HTTP Protocol)** والأمان (Security)، وتصميم معماريات الـ APIs.

دعنا نفكك الفروقات الجوهرية بينهما بأعلى هندسة وبأبسط أسلوب.

## 1. التشبيه العبقري (البطاقة البريدية المكشوفة vs. الطرد الصندوقي المغلق)

- **طلب الـ `GET`:** يشبه تماماً **"البطاقة البريدية (Postcard)"**. تكتب الرسالة على كرت مكشوف، يراها ساعي البريد، ويراها أي شخص يمسكها في الطريق. تصلح للرسائل القصيرة وغير السرية (مثل إرسال تحية أو البحث عن عنوان).
- **طلب الـ `POST`:** يشبه **"الطرد البريدي المغلق داخل صندوق كرتوني (Sealed Parcel)"**. محتويات الرسالة بالداخل، لا أحد يراها من الخارج أثناء نقلها في الشاحنة. تصلح للأشياء الثمينة، السرية، أو الضخمة.

## 2. جدول الفروقات الهندسي الشامل

هذا الجدول يلخص كيف يرى المتصفح والسيرفر كل نوع طلب:

| وجه المقارنة | طلب الـ `GET` | طلب الـ `POST` |
| --- | --- | --- |
| **مكان إرسال البيانات** | تُرسل ملتصقة بالرابط **(URL Query String)**.
مثال: `search?q=phone` | تُرسل مخفية داخل **جسم الطلب (Request Body)**. |
| **الأمان والسرية (Security)** | **غير آمن للبيانات الحساسة**؛ لأن البيانات تظهر علناً في شريط الرابط، وتُحفظ في سجل المتصفح (History). | **أكثر أماناً**؛ البيانات لا تظهر في الرابط ولا تُحفظ في سجل المتصفح (لكنها لا تزال تحتاج لتشفير HTTPS). |
| **حجم البيانات (Data Size)** | **محدود جداً** (حوالي 2048 حرفاً كحد أقصى حسب المتصفح والسيرفر). | **غير محدود** (يمكنك إرسال نصوص ضخمة، ملفات، وصور). |
| **الحفظ في المفضلة (Bookmarking)** | **ممكن**؛ يمكنك حفظ الرابط بالبيانات التي فيه ومشاركتها مع صديق (مثل نتائج بحث جوجل). | **غير ممكن**؛ إذا حفظت الرابط فلن تُحفظ البيانات الحساسة المرسلة معه. |
| **تأثير المعالجة (Idempotency)** | **آمن (Safe/Idempotent)**؛ تكرار الطلب يجلب نفس البيانات دون تغيير حالة السيرفر (مثل القراءة). | **غير آمن (Non-Idempotent)**؛ تكرار الطلب يُحدث تغييراً في السيرفر (مثل إضافة منشور جديد أو سحب أموال). |

## 3. شرح السلوك الهندسي الحرج (معماريًا)

هنا سيسألك الـ Interviewer: **"متى أختار GET ومتى أختار POST؟"**

- **قاعدة الـ `GET` الذكية:** تُستخدم **لجلب واستعراض البيانات فقط (Read Operations)**. عندما يكتب المستخدم كلمة بحث، أو يضغط على تصنيف منتجات، أو يفتح صفحة بروفايل. الـ `GET` لا يغير أي شيء في قاعدة البيانات على السيرفر.
- **قاعدة الـ `POST` الذكية:** تُستخدم **لإرسال وتعديل البيانات (Write/Create Operations)**. عندما يكتب المستخدم كلمة مرور، أو يرفع ملف PDF، أو يضغط على "تأكيد الشراء وتحويل الأموال". الـ `POST` يغير حالة السيرفر أو قاعدة البيانات.

## الكلمات المفتاحية للحفظ (Keywords)

- **`Query String`**: سلسلة البيانات الملحقة بنهاية الـ URL في طلبات GET.
- **`Request Body`**: جسم الطلب المغلق الذي يحمل بيانات الـ POST.
- **`Idempotent`**: خاصية تعني أن تكرار الطلب لا يسبب أضراراً جانبية أو تغييرات متكررة بالسيرفر (خاصة بـ GET).
- **`Browser History & Caching`**: قابلية تخزين الطلب في سجل المتصفح وكاش المتصفح (ميزة لـ GET، خطر لـ POST).

> **جملتك النموذجية في المقابلة:**
"The core difference between **GET** and **POST** lies in intent, security, and data handling. **GET** is designed to **retrieve data**; it appends parameters directly to the URL as a **query string**, meaning it has strict size limits, gets saved in browser history, and is **not secure** for sensitive data. It is also **idempotent**, meaning repeated requests don't change the server state. Conversely, **POST** is used to **send or modify data**; it encapsulates payloads securely inside the **HTTP Request Body**, has no size limitations, supports file uploads, and cannot be cached or bookmarked, making it the industry standard for logins, forms, and data creation
>

# الشرح بالتفصيل

وصلنا للسؤال الثالث في قسم **`4.4 Form Submission`**، وهو السلسلة النصية التي نراها يومياً في شريط عناوين المتصفح: **`What is a Query String?`**.

في المقابلات الشخصية، يُطرح هذا السؤال لاختبار مدى فهمك لكيفية تمرير البيانات والمعاملات (Parameters) بين صفحات الموقع أو إلى السيرفر عبر الـ URL مباشرة، وخاصة عند استخدام طلبات الـ `GET`.

تعال نفصص الـ `Query String` بأعلى عمق هندسي وبأسهل أسلوب.

## 1. التشبيه العبقري (اللاصقة الإرشادية على الطرد)

تخيل لو أنك أرسلت طرداً كرتونياً مغلقاً لصديقك، ولكنك قمت بلصق ورقة صغيرة على السطح الخارجي للصندوق مكتوب عليها بخط عريض:
`نوع المحتوى: لابتوب | الصفحة رقم: 2` (هذا هو الـ **`/search?q=laptop&page=2`**).
أي شخص يحمل الصندوق أو يمر بجانبه يستطيع قراءة هذه المعلومات فوراً بمجرد النظر لسطح الصندوق دون الحاجة لفتحه. هي معلومات مكشوفة وواضحة والهدف منها إرشاد السيرفر بكيفية فرز وعرض المحتوى بالداخل.

الـ `Query String` هي هذه الورقة اللاصقة المكتوبة علناً فوق رابط الـ URL.

## 2. التحليل الهيكلي والتفكيك البرمجي (من كودك الممتاز)

في مثالك المثالي والواضح جداً:

Plaintext

```
/search?q=laptop&page=2
```

المتصفح والسيرفر يقرآن هذا العنوان ويقومان بتفكيكه بناءً على رموز برمجية قياسية صارمة:

1. **علامة الاستفهام (`?`):** هي نقطة التحول والمفتاح الفاصل. تخبر المتصفح: *"انتهى مسار الصفحة الرئيسي (Path)، وكل ما سيأتي بعد هذا الرمز هو عبارة عن بيانات ومعاملات (Query Parameters)"*.
2. **الثنائيات المكونة من مفتاح وقيمة (Key-Value Pairs):** البيانات تُرتب دائماً على هيئة ثنائية:
    - **`q`** (المفتاح الأول - Key): قيمته هي `laptop`.
    - **`page`** (المفتاح الثاني - Key): قيمته هي `2`.
3. **علامة اليساوي (`=`):** تُستخدم للربط بين المفتاح وقيمته.
4. **علامة الـ Ampersand (`&`):** تُستخدم كفاصل للفصل بين المتغيرات المختلفة (لتخبر السيرفر بأن المتغير الأول انتهى وبدأ متغير جديد).

## 3. أشهر حالات الاستخدام في المشاريع الحقيقية 🚀

بصفتك مهندس برمجيات، اذكر للمقابل هذه الحالات الحية لـ الـ `Query String`:

- **محركات البحث والفلاتر (Search & Filtering):** مثل مثالك الممتاز؛ عندما تبحث في موقع تجارة إلكترونية، يتم تمرير كلمة البحث والصفحة الحالية للتنقل بين الصفحات (Pagination).
- **التتبع والحملات التسويقية (Marketing Tracking):** روابط الإعلانات التي تضغط عليها على فيسبوك تحتوي دائماً على معاملات تسمى `utm_source` أو `utm_medium` داخل الـ Query String لمعرفة مصدر الزيارة.
- **الوضع الداكن والفاتح (UI State):** أحياناً يتم تمرير متغير مثل `?theme=dark` لتخبر الصفحة الجديدة بتفعيل التصميم المظلم فور تحميلها.

## 💡 تريكة المحترفين: تشفير الرموز الخاصة (URL Encoding)

المتصفح لا يقبل المسافات أو الرموز الخاصة (مثل `@` أو `#` أو المسافة الفاضية) داخل رابط الـ URL.

- لو بحث المستخدم عن: `laptop lenovo`
- المتصفح برمجياً سيحول المسافة إلى رمز خاص وتتحول الـ Query String إلى:
`?q=laptop%20lenovo` (حيث `%20` هو الترميز القياسي للمسافة). هذه العملية تسمى **URL Encoding**.

## الكلمات المفتاحية للحفظ (Keywords)

- **`Query Parameters`**: معاملات الاستعلام المكونة من مفتاح وقيمة (Key-Value).
- **`The Question Mark Separator (?)`**: علامة الاستفهام الفاصلة بين المسار والمعاملات.
- **`The Ampersand (&)`**: رمز الربط والفصل بين المعاملات المتعددة.
- **`URL Encoding`**: عملية تحويل الرموز الخاصة والمسافات إلى صيغة يقبلها الـ URL.

> **جملتك النموذجية في المقابلة:**
"A **Query String** is the part of a URL that contains data to be passed to the web server, typically appearing after a question mark **(`?`)**. In the example **`/search?q=laptop&page=2`**, the data is structured in **key-value pairs** separated by an ampersand **(`&`)**, where `q` equals `laptop` and `page` equals `2`. It is primarily used with HTTP **GET** requests for non-sensitive tasks like search queries, filtering, sorting, or pagination. Since it is visible in the address bar, it undergoes **URL Encoding** to safely represent spaces and special characters
>

# What is a Request Body?

# الشرح بالتفصيل

كمل السؤال الرابع

What is a Request Body?

وصلنا للسؤال الرابع في قسم **`4.4 Form Submission`**، وهو المكان السري والآمن الذي تُخزن فيه البيانات الضخمة والحساسة أثناء انتقالها عبر الشبكة: **`What is a Request Body?`**.

في المقابلات الشخصية، يُطرح هذا السؤال لاختبار مدى فهمك لهيكل بروتوكول HTTP وكيفية نقل البيانات بشكل خفي ومنظم، وهو المفهوم المقابل تماماً للـ `Query String` التي تظهر علناً في الرابط.

تعال نفصص الـ `Request Body` بأعلى عمق هندسي وأسهل أسلوب.

## 1. التشبيه العبقري (رسالة داخل مغلف مغلق)

تخيل لو أنك تريد إرسال رسالة تحتوي على "رقم بطاقتك الائتمانية" و"تفاصيل حسابك" لصديقك:

- **إذا استخدمت الـ Query String:** كأنك كتبت هذه البيانات على الجزء الخارجي المكشوف من بطاقة بريدية؛ أي شخص يمسكها في الطريق يستطيع قراءتها بسهولة.
- **إذا استخدمت الـ Request Body:** كأنك كتبت البيانات في أوراق متعددة، ووضعتها داخل **"مغلف ورقي سميك ومغلق (Envelope)"**. الشخص الذي ينقل الرسالة لا يرى سوى عنوان المستلم من الخارج، أما التفاصيل والبيانات الحساسة فهي مخبأة بأمان في الداخل ولا تظهر إلا عندما يفتح المستلم (السيرفر) هذا المغلف.

الـ `Request Body` هو هذا المغلف المغلق الذي يحمل تفاصيل الرسالة بعيداً عن الأعين.

## 2. الهيكل الفني والبرمجي (Behind the Scenes)

عندما يرسل المتصفح طلب من نوع **`POST`** أو **`PUT`**، فإنه يبني رسالة HTTP تتكون من جزأين رئيسيين يفصل بينهما سطر فارغ:

1. **الـ Headers (الرأس):** تحتوي على معلومات وصفية حول الطلب (مثل نوع المتصفح، العنوان المستهدف، ونوع تشفير البيانات `Content-Type`).
2. **الـ Body (الجسد):** وهو بطلنا اليوم! هو الجزء الذي تقع فيه البيانات الفعلية المجمعة من الـ Form.

إذا كانت البيانات مرسلة من فورم تسجيل دخول (Login Form)، فسيكون شكل طلب الـ HTTP الخام المرسل للسيرفر كالتالي:

HTTP

```
POST /api/login HTTP/1.1
Host:mysite.com
Content-Type:application/x-www-form-urlencoded
Content-Length:45

username=Hanan+Awad&password=SuperSecret12345
```

*(لاحظ كيف أن اسم المستخدم وكلمة المرور مخفيان تماماً في الجزء السفلي "الجسد" ولم يظهرا في الرابط الرئيسي `/api/login` في الأعلى).*

## 3. لماذا نستخدم الـ `Request Body` في المشاريع الحقيقية؟

- **حماية البيانات الحساسة (Security & Privacy):** لمنع ظهور كلمات المرور، أرقام البطاقات، أو البيانات الشخصية في شريط عنوان المتصفح، أو حفظها في سجلات المتصفح (Browser History) وسجلات الخوادم (Server Logs).
- **رفع الملفات والوسائط (File Uploads):** ملفات الصور، الفيديو، والـ PDF حجمها ضخم جداً ويتكون من بيانات ثنائية (Binary Data). الـ URL مستحيل أن يتحملها، لذا فإن المكان الوحيد القادر على حمل هذه الملفات الضخمة هو الـ `Request Body` باستخدام تشفير خاص يسمى `multipart/form-data`.
- **دعم تنسيقات البيانات الحديثة (مثل JSON):** عند بناء تطبيقات حديثة تعتمد على الجافاسكريبت (مثل React أو Vue)، نقوم بإرسال البيانات للسيرفر على هيئة كائن JSON منظم داخل الـ `Request Body` هكذا:JSON
    
    ```
    {
      "username": "Hanan Awad",
      "email": "hanan@example.com"
    }
    ```
    

## الكلمات المفتاحية للحفظ (Keywords)

- **`HTTP Request Payload`**: حمولة البيانات الفعلية المرسلة في طلب الـ HTTP.
- **`Content-Type Header`**: الهيدر الوصفي الذي يحدد للسيرفر كيفية قراءة وفك تشفير الـ Body (مثل `application/json` أو `multipart/form-data`).
- **`Data Encapsulation`**: كبسلة وإخفاء البيانات داخل هيكل الطلب بعيداً عن الـ URL.
- **`Unlimited Payload Size`**: عدم وجود قيود صارمة على حجم البيانات مقارنة بالـ URL.

> **جملتك النموذجية في المقابلة:**
"The **`Request Body`** (or payload) is the data area of an HTTP request that carries the actual data submitted by a client to the server, typically used with **POST**, **PUT**, or **PATCH** methods. Unlike query strings, the data inside the Request Body is encapsulated and hidden from the URL, preventing it from being cached or stored in the browser history. It is crucial for **security** (like transmitting passwords) and is the only vehicle capable of handling **large datasets** and **file uploads** (using `multipart/form-data`) or modern structured data formats like **JSON**
>

# What is the `enctype` attribute?

# **الشرح بالتفصيل**

وصلنا للسؤال الخامس في قسم **`4.4 Form Submission`**، وهو السمة المسؤولة عن تحديد "لغة التشفير" والتهيئة التي ستُحزم بها البيانات قبل شحنها: **`What is the enctype attribute?`**.

في المقابلات الشخصية، يُطرح هذا السؤال لاختبار مدى فهمك لكيفية نقل الملفات والوسائط (File Uploads) عبر الشبكة، وهو من الأسئلة التي تفرز المطور الذي يفهم بروتوكول HTTP جيداً عن غيره.

تعال نفصص الـ `enctype attribute` بأعلى عمق هندسي وبأسهل أسلوب.

## 1. التشبيه العبقري (لغة التغليف والتعبئة)

تخيل أنك تريد شحن ثلاثة أشياء مختلفة لصديقك: (خطاب ورقي، ومفتاح معدني، وباقة ورد طبيعية).

- هل ستضعهم جميعاً في نفس الظرف الورقي الرفيع؟ بالطبع لا!
- الخطاب الورقي يحتاج لظرف عادي (هذا هو التشفير الافتراضي).
- أما الورد والمفتاح فيحتاجان إلى صندوق كرتوني مبطن ومقسم بطريقة معينة ليتحمل المواد الصلبة والسوائل دون تلف (هذا هو تشفير الملفات).

الـ **`enctype`** (اختصار لـ **Encoding Type**) هو الذي يخبر المتصفح: **"ما هي طريقة التعبئة والتغليف المناسبة لنوع البيانات الموجودة داخل هذه الاستمارة قبل إرسالها؟"**.

## 2. القيم الثلاث الأساسية للـ `enctype` (مادة المقابلات الدسمة!)

هناك ثلاث قيم قياسية تفهمها المتصفحات والسيرفرات، ويجب عليك معرفتها بالتفصيل:

### أ. `application/x-www-form-urlencoded` (الوضع الافتراضي - Default)

- **متى يُستخدم؟** إذا لم تكتب سمة `enctype` في الـ `<form>`، فهذه هي القيمة الافتراضية التي يختارها المتصفح تلقائياً.
- **كيف يعمل؟** يقوم بتحويل كل الحروف والمسافات إلى رموز خاصة بترميز الـ URL (مثل تحويل المسافة إلى `+` أو `%20` وتحويل الرموز الخاصة كالتالي: `&` تصبح `%26`).
- **مثال لشكل البيانات المرسلة:**Plaintext
    
    ```
    username=Hanan+Awad&city=Cairo
    ```
    
- **ملاحظة:** ممتاز للنصوص القصيرة، لكنه **سيئ جداً وغير صالح نهائياً لرفع الملفات**.

### ب. `multipart/form-data` (بطل رفع الملفات 🌟)

- **متى يُستخدم؟** **إلزامياً** عندما يحتوي النموذج الخاص بك على حقل رفع ملفات مثل: `<input type="file">`.
- **كيف يعمل؟** يقوم بتقسيم طلب الـ HTTP إلى أجزاء متعددة (Multi-parts). كل حقل نصي يأخذ جزأه الخاص، والملف الثنائي (Binary File) يتم تشفيره وإرساله ككتلة بيانات منفصلة ومحمية بحدود عشوائية (Boundaries) يضعها المتصفح لكي يستطيع السيرفر فك تفاصيلها.
- **⚠️ قاعدة المقابلات الذهبية:** لو نسيت كتابة `enctype="multipart/form-data"` في فورم يحتوي على حقل رفع صور، **فلن يتم رفع أي ملف للسيرفر نهائياً**، وسيرسل المتصفح اسم الملف فقط كنص فارغ!

### ج. `text/plain` (الترميز البسيط جداً)

- **متى يُستخدم؟** نادراً جداً في التطبيقات الحديثة (يستخدم أحياناً لأغراض تصحيح الأخطاء - Debugging).
- **كيف يعمل؟** يرسل البيانات كما هي بشكل نصي خام دون أي ترميز أو تشفير (دون تحويل المسافات أو الرموز الخاصة).

## 3. شروط تفعيل الـ `enctype`

لكي تعمل سمة الـ `enctype` وتؤدي وظيفتها، يجب أن يتوفر شرطان أساسيان في الـ `<form>`:

1. أن تكون السمة مكتوبة داخل عنصر الـ `<form>` نفسه.
2. أن تكون طريقة الإرسال هي **`method="POST"`** حصراً. (لأن الـ `enctype` لا يعمل مع طلبات الـ `GET` التي تعتمد افتراضياً على تضمين البيانات في الـ URL مباشرة).

## الكلمات المفتاحية للحفظ (Keywords)

- **`Encoding Type (enctype)`**: نوع ترميز بيانات النموذج قبل الشحن.
- **`application/x-www-form-urlencoded`**: الترميز الافتراضي للنصوص والبيانات البسيطة.
- **`multipart/form-data`**: الترميز الإلزامي لرفع الملفات والبيانات الثنائية (Binary Data).
- **`HTTP POST Method Requirement`**: إلزامية استخدام POST لتفعيل ترميز الملفات.

> **جملتك النموذجية في المقابلة:**
"The **`enctype` attribute** (Encoding Type) specifies how form-data should be encoded before sending it to the server. It is only functional when **`method="POST"`** is used. The default value is **`application/x-www-form-urlencoded`**, which converts characters into URL-encoded strings, perfect for text. However, when building forms that include file uploads (`<input type="file">`), we must explicitly set **`enctype="multipart/form-data"`**. This forces the browser to split the payload into distinct parts, allowing binary file data to be transmitted alongside textual input. Forgetting this attribute is a common mistake that results in files not being uploaded to the server."
>

تعال نفصص مفهوم الـ Form Validation بأعلى عمق هندسي وبأسهل أسلوب.

## 1. التشبيه العبقري (موظف الجوازات في المطار)

تخيل لو أنك مسافر إلى دولة ما. قبل أن تركب الطائرة وتصل إلى حدود تلك الدولة، هناك **"موظف فحص عند بوابة الطائرة (Client-side Validation)"**:

- يفحص جواز سفرك: هل هو صالح؟ هل يحتوي على تأشيرة؟ هل اسمك مكتوب بشكل صحيح؟
- إذا وجد خطأ (مثلاً جواز سفرك منتهي الصلاحية)، سيمنعك فوراً من ركوب الطائرة ويقول لك: *"عذراً، أصلح جواز سفرك أولاً ثم عد إلينا"* ليوفر عليك عناء السفر هباءً.

ولكن، بمجرد وصولك هناك، يوجد **"ضابط الهجرة داخل نظام الدولة (Server-side Validation)"**؛ يقوم بفحصك مجدداً بدقة أعلى عبر قواعد البيانات الرسمية للتأكد من أنك لست مدرجاً في قوائم الحظر.

الـ **`Form Validation`** هو عملية الفحص والتدقيق هذه؛ للتأكد من أن البيانات تطابق المعايير المطلوبة تماماً قبل السماح لها بالدخول إلى قاعدة البيانات.

## 2. المستويان الهندسيان للتحقق (The Dual-Layer Architecture)

بصفتك مهندس برمجيات محترف، يجب أن تشرح للمقابل أن التحقق لا يحدث في مكان واحد، بل ينقسم إلى طبقتين متكاملتين:

### أ. التحقق في الواجهة الأمامية (Client-Side Validation)

- **أين يحدث؟** داخل متصفح المستخدم مباشرة (باستخدام سمات HTML5 مثل `required`, `pattern` أو باستخدام JavaScript).
- **الهدف الأساسي:** **تحسين تجربة المستخدم (UX)**. هو يقدم رد فعل فوري ولحظي للمستخدم (Instant Feedback). لو نسي المستخدم كتابة رمز `@` في الإيميل، يخبره المتصفح فوراً دون الحاجة لانتظار إرسال البيانات للسيرفر وإعادة تحميل الصفحة.
- **⚠️ حقيقة علمية:** هذه الطبقة **سهلة الاختراق تماماً** ويمكن لأي مستخدم محترف تعطيلها بضغطة زر عبر أدوات المطورين (DevTools).

### ب. التحقق في الخلفية (Server-Side Validation)

- **أين يحدث؟** على خادم الويب (السيرفر) باستخدام لغة البرمجة الخاصة بالباكيند (مثل Node.js, PHP, Python) وقبل إدخال البيانات لقاعدة البيانات.
- **الهدف الأساسي:** **الأمان والحماية المطلقة (Security & Data Integrity)**. هو جدار الحماية الحقيقي الذي لا يمكن للمستخدم تجاوزه أو التلاعب به. يحمي الموقع من الاختراقات (مثل SQL Injection) ويضمن عدم دخول بيانات تالفة أو خبيثة للنظام.

## 3. ما هي أنواع التحقق (Validation Types)؟

تتأكد عملية الـ Validation من ثلاثة أشياء رئيسية في البيانات:

1. **الوجود (Presence):** هل الحقل المطلوب تم ملؤه أم تُرك فارغاً؟ (`required`)
2. **الصيغة والشكل (Format/Pattern):** هل الإيميل مكتوب بصيغة إيميل حقيقية؟ هل رقم الهاتف يتكون من أرقام فقط؟ (`type="email"`, `pattern`)
3. **القيود والمدى (Range/Length):** هل كلمة المرور طويلة كفاية؟ هل عمر المستخدم أكبر من 18 عاماً؟ (`minlength`, `min`)

## الكلمات المفتاحية للحفظ (Keywords)

- **`Client-Side Validation`**: التحقق في طرف العميل (المتصفح) لتحسين الـ UX.
- **`Server-Side Validation`**: التحقق في طرف الخادم (السيرفر) لضمان الأمان والـ Security.
- **`Instant Feedback`**: التغذية الراجعة الفورية للمستخدم عند ارتكاب خطأ.
- **`Data Integrity`**: سلامة وصحة البيانات وضمان مطابقتها لقواعد النظام.

> **جملتك النموذجية في المقابلة:**
"Conseptually, **Form Validation** is the process of verifying that user input meets specific criteria and constraints before it is processed or stored. Architecturally, it must be implemented in a **dual-layer strategy**. First, **Client-Side Validation** runs in the browser using HTML5 attributes or JavaScript to provide **instant feedback** and enhance the User Experience (UX). Second, **Server-Side Validation** is executed strictly on the backend as the ultimate line of defense for **security and data integrity**, ensuring that bypassed or malicious client requests are blocked before interacting with the database
>

# **الشرح بالتفصيل**

وصلنا للسؤال الثاني في قسم **`4.5 Form Validation`**، وهو النظام المدمج والذاتي الذي يأتي بداخل المتصفح تلقائياً دون أي جهد برمجي إضافي: **`What is Native Validation?`**.

في المقابلات الشخصية، يحب الـ Interviewer طرح هذا السؤال ليرى ما إذا كنت كمهندس واجهات تستفيد من القوة الافتراضية للمتصفح (Native Power)، أم أنك تسارع لكتابة مئات السطور من أكواد الجافاسكريبت والمكتبات الخارجية دون داعٍ.

تعال نفصص مفهوم الـ `Native Validation` بأعلى عمق هندسي وبأسهل أسلوب.

## 1. التشبيه العبقري (نظام الملاحة المدمج في السيارة)

تخيل لو أنك اشتريت سيارة حديثة، ووجدت فيها نظام ملاحة (GPS) وخرائط مدمجاً بداخل شاشة السيارة الأصلية ومصمماً من الشركة المصنعة للسيارة نفسها (هذا هو الـ **`Native Validation`**).

- إنه يعمل فوراً بمجرد تشغيل السيارة.
- خفيف وسريع ولا يستهلك بطارية إضافية.
- لا يتطلب منك تنزيل تطبيقات خارجية أو دفع اشتراكات.

قد لا يكون فيه كل الأشكال الجمالية المخصصة التي تحلم بها، ولكنه موثوق، سريع، ويؤدي الغرض الأساسي بكفاءة وبدون أي وزن زائد!

## 2. التحليل الهيكلي والسلوكي (من كودك الممتاز)

في مثالك المثالي والمختصر جداً (مع تصحيح المسافة البسيطة في الـ Input):

HTML

```
<input type="email" required>
```

بمجرد كتابة هذا السطر البسيط، يتولى محرك المتصفح (مثل Blink أو WebKit) تشغيل الـ **`Native Validation Engine`** ويقوم بـ:

1. **مراقبة الحالة (Constraint Validation API):** المتصفح يقوم فوراً بتفعيل واجهة برمجية مدمجة تراقب هذا الحقل. يضع المتغير `valid` كـ `false` ما دام الحقل فارغاً، أو إذا كُتب فيه نص لا يحتوي على رمز `@` وصيغة بريد إلكتروني سليمة.
2. **الاعتراض التلقائي (Automatic Blocking):** عند محاولة إرسال النموذج (Submit) والبيانات غير سليمة، يعترض المتصفح الطلب برمجياً بشكل فوري ويمنعه من الوصول للشبكة.
3. **توليد تنبيهات واجهة المستخدم المدمجة (Native Tooltips):** يظهر المتصفح فقاعة تنبيهية (Tooltip) مصممة ومترجمة تلقائياً بلغة جهاز المستخدم (مثلاً يظهر بالكامل بالعربية: *"يُرجى إدخال عنوان بريد إلكتروني"* إذا كانت لغة المتصفح عربية).

## 3. مميزات وعيوب الـ Native Validation (تريكة المقابلات!)

لكي تظهر بمظهر المهندس المحترف والمحنك، لخص للمقابل الموازنة الفنية للتحقق المدمج:

### المميزات (The Pros):

- **أداء خارق (Zero-JS Performance):** خفيف جداً ولا يضيف أي كيلوبايت لملفات الجافاسكريبت الخاصة بموقعك.
- **إتاحة وصول ممتازة (Built-in Accessibility - a11y):** متوافق تلقائياً مع قارئات الشاشة (Screen Readers) ومستخدمي لوحة المفاتيح.
- **الترجمة التلقائية (Localization):** المتصفح يترجم رسائل الخطأ تلقائياً للغة التي يفضلها المستخدم دون تدخل منك.

### العيوب (The Cons):

- **صعوبة التخصيص البصري (Styling Limitations):** من الصعب جداً جعل شكل فقاعة الخطأ (Tooltip) متطابقاً 100% مع الهوية البصرية الفريدة (Brand UI) الخاصة بالعميل بشكل موحد عبر كل المتصفحات (كروم، سفاري، فايرفوكس).
- **اختلاف الرسائل (Inconsistency):** شكل ورسالة الخطأ تختلفان بشكل طفيف بين مستخدم يتصفح من هاتف آيفون (Safari) وآخر من كمبيوتر بنظام ويندوز (Chrome).

## الكلمات المفتاحية للحفظ (Keywords)

- **`Native Browser Engine`**: المحرك الداخلي للمتصفح الذي يدير التحقق تلقائياً.
- **`Constraint Validation API`**: الواجهة البرمجية المدمجة في المتصفح لفحص قيود الحقول.
- **`Zero-JS Overhead`**: ميزة الفحص والتحقق دون تحميل أي أكواد جافاسكريبت إضافية.
- **`Localization Support`**: الدعم المدمج لترجمة رسائل الأخطاء للغة جهاز المستخدم.

> **جملتك النموذجية في المقابلة:**
"The **`Native Validation`** refers to the built-in form validation capabilities provided directly by the browser's engine without relying on external JavaScript or libraries. In the example **`<input type="email" required>`**, the browser automatically leverages its **Constraint Validation API** to block form submission if the field is empty or doesn't match a standard email format. It is highly beneficial due to its **zero-JS performance footprint** and built-in **accessibility (a11y)**. However, as UI Engineers, we must account for its limitations in **styling consistency**, as the visual appearance of native error tooltips varies across different browsers and operating systems."

# السؤال الثالث

# What is the Constraint Validation API?

# **الشرح بالتفصيل**

وصلنا للسؤال الثالث في قسم **`4.5 Form Validation`**، وهو العقل المدبر والمحرك الداخلي الذي يربط بين الـ HTML والـ JavaScript في عملية التحقق: **`What is the Constraint Validation API?`**.

في المقابلات الشخصية، عندما تسأل عن هذا المفهوم، فإن الـ Interviewer يتوقع منك أن تتجاوز مجرد استخدام سمات الـ HTML البسيطة لتثبت قدرتك على **التحكم البرمجي الكامل** في عملية التحقق وتخصيص تجربة المستخدم (UX) باستخدام الجافاسكريبت.

تعال نفصص الـ `Constraint Validation API` بأعلى عمق هندسي وبأسهل أسلوب.

## 1. التشبيه العبقري (لوحة العدادات وأجهزة الاستشعار في السيارة)

تخيل لو أنك تقود سيارة حديثة؛ بداخل المحرك والفرامل توجد مجموعة من أجهزة الاستشعار (Sensors). على لوحة العدادات أمامك (Dashboard)، تظهر لك لمبات تحذيرية:

- لمبة البنزين تضيء باللون الأصفر إذا شارف على الانتهاء.
- لمبة المحرك تضيء باللون الأحمر في حال وجود عطل.
- الأهم من ذلك، لو أردت كمسؤول صيانة، يمكنك توصيل كمبيوتر خاص بالسيارة (عن طريق منفذ OBD) لقراءة تقارير تفصيلية برقم الكود والخطأ المحدد وتعديل سلوك السيارة برمجياً.

الـ **`Constraint Validation API`** هي كمبيوتر الفحص المدمج هذا؛ إنها مجموعة من الخصائص (Properties) والأساليب (Methods) البرمجية التي يوفرها المتصفح لكل حقل إدخال، وتتيح لك كـ Developer الاستعلام عن حالة الحقل برمجياً وتعديل رسائل الخطأ بالكامل من خلال الـ JavaScript.

## 2. كيف تعمل خلف الكواليس؟ (The Architecture)

بمجرد استخدامك للـ HTML5 Native Validation (مثل `required` أو `pattern`)، يقوم المتصفح تلقائياً بإنشاء كائن برمجي مرتبط بكل عنصر إدخال في الـ DOM. تتيح لك هذه الـ API قراءة والتحكم في الخصائص التالية عبر الـ JS:

### أ. الخاصية الأكثر أهمية: `element.validity` (جهاز فحص الأخطاء)

هذه الخاصية عبارة عن كائن (Object) يحتوي على مجموعة من الـ Booleans (True/False) التي توضح بدقة شديدة نوع الخطأ الحالي في الحقل. إليك أهم خصائصه الفرعية:

- `valueMissing`: قيمتها `true` إذا كان الحقل يحمل سمة `required` وتركه المستخدم فارغاً.
- `typeMismatch`: قيمتها `true` إذا أدخل المستخدم نصاً لا يتطابق مع نوع الحقل (مثل كتابة اسم عادي في حقل `type="email"`).
- `tooShort` / `tooLong`: قيمتها `true` إذا لم يلتزم المستخدم بالحد الأدنى (`minlength`) أو الأقصى (`maxlength`).
- `patternMismatch`: قيمتها `true` إذا لم يطابق الإدخال التعبير النمطي المكتوب في الـ `pattern`.
- `valid`: قيمتها `true` فقط إذا كان الحقل سليماً تماماً ومجتازاً لكل الفحوصات بنجاح.

### ب. الخاصية: `element.validationMessage`

- تحتوي على النص الفعلي لرسالة الخطأ التي سيظهرها المتصفح للمستخدم حالياً (مثال: *"Please fill out this field"*).

### ج. الطريقة البرمجية الأهم: `element.setCustomValidity(message)`

- هذا هو المفتاح السحري! تتيح لك هذه الدالة **تجاوز رسالة خطأ المتصفح الافتراضية ووضع رسالة مخصصة تماماً من إنشائك**، أو حتى وضع خطأ برمجي مخصص بناءً على شروط منطقية خاصة بك (Business Logic) لا يمكن للـ HTML القيام بها بمفرده.
- *تريكة المقابلات:* إذا مررت نصاً فارغاً لهذه الدالة هكذا `setCustomValidity("")` فإن المتصفح يعتبر الحقل سليماً وصالحاً (Valid) فوريّاً.

## 3. مثال برمجي سريع يوضح القوة الحقيقية للـ API 🛠️

تخيل لو نريد حقل إدخال لـ "اسم المستخدم" بحيث يظهر خطأ مخصصاً بالكامل بلغة وتصميم موقعنا إذا تُرك فارغاً:

JavaScript

```
const usernameInput = document.querySelector("#username");

usernameInput.addEventListener("input", () => {
  if (usernameInput.validity.valueMissing) {
    // تخصيص رسالة الخطأ فوراً عبر الـ API
    usernameInput.setCustomValidity("عذراً، لا يمكنك ترك حقل اسم المستخدم فارغاً!");
  } else {
    // مسح الخطأ وجعل الحقل صالحاً (Valid) بمجرد الكتابة
    usernameInput.setCustomValidity("");
  }
});
```

| --- | --- | --- |
| **`valueMissing`** | إذا ترك المستخدم الحقل فارغاً وهو مطلوب. | `required` |
| **`typeMismatch`** | إذا أدخل نصاً لا يطابق نوع الحقل (مثل إدخال نص عادي في حقل إيميل). | `type="email"` أو `type="url"` |
| **`patternMismatch`** | إذا لم يطابق الإدخال التعبير النمطي (RegEx) المحدد للحقل. | `pattern="[0-9]{5}"` |
| **`tooLong`** | إذا تجاوز النص المكتوب الحد الأقصى المسموح به من الحروف. | `maxlength` |
| **`tooShort`** | إذا كان النص المكتوب أقصر من الحد الأدنى المطلق للحروف. | `minlength` |
| **`rangeUnderflow`** | إذا كانت القيمة الرقمية أقل من الحد الأدنى المسموح به. | `min` |
| **`rangeOverflow`** | إذا كانت القيمة الرقمية أعلى من الحد الأقصى المسموح به. | `max` |
| **`stepMismatch`** | إذا كانت القيمة لا تتماشى مع خطوة الزيادة والنقصان المحددة. | `step` |
| **`customError`** | إذا قمتِ أنتِ بتعيين خطأ مخصص يدوياً (كما تعلمنا في السؤال السادس!). | `setCustomValidity("error")` |
| **`valid`** | **الملك الحاكم:** تكون `true` فقط إذا كانت جميع الخصائص السابقة `false` (أي الحقل سليم 100%). | سليم وخالٍ من الأخطاء |

## 3. مثال عملي يوضح قوة `input.validity`

لنفرض أن لدينا هذا الحقل في صفحتكِ:

HTML

```
<input type="email" id="userEmail" required minlength="10">
```

إذا كتب المستخدم داخل الحقل حرفين فقط مثل `"abc"` وحاول الإرسال، فلنرى ماذا سيخبرنا كائن الـ `validity` في الجافاسكريبت:

JavaScript

```
const emailInput = document.getElementById("userEmail");

// نلقي نظرة على لوحة تحكم الـ validity حالياً:
console.log(emailInput.validity.valueMissing);  // false (الحقل ليس فارغاً، به "abc")
console.log(emailInput.validity.typeMismatch);  // true  (مخالفة! النص "abc" ليس بريداً إلكترونياً صالحاً)
console.log(emailInput.validity.tooShort);      // true  (مخالفة! النص أقصر من 10 حروف)
console.log(emailInput.validity.valid);         // false (الحقل غير صالح إجمالاً لوجود أخطاء)
```

بفضل هذه الخصائص، يمكنكِ إظهار رسائل مخصصة وتصميم واجهات مستخدم مذهلة بناءً على نوع الخطأ المرتكب تحديداً!

## الكلمات المفتاحية للحفظ (Keywords)

- **`ValidityState Object`**: الكائن البرمجي المرجعي الذي ترجعه خاصية `validity` والمليء بحالات الفحص المنطقية.
- **`Read-only Flags`**: الخصائص التي لا يمكن تعديلها مباشرة بل نقرأ قيمتها فقط لمعرفة الخطأ.
- **`valueMissing & typeMismatch`**: أشهر فحصين يُستخدمان للتحقق من خلو الحقل ومطابقة نوعه.
- **`valid Flag`**: المؤشر النهائي لصلاحية الحقل بالكامل.

> **جملتك النموذجية في المقابلة:**
> 
> 
> "The **`validity`** property returns a **`ValidityState`** object, which contains a set of read-only boolean flags representing the validation state of an input element. Instead of just knowing whether an input is valid or not, this object allows us to pinpoint the exact reason for the failure. For instance, if a required field is empty, **`validity.valueMissing`** becomes `true`. If the format is wrong, **`validity.typeMismatch`** is triggered. Ultimately, **`validity.valid`** acts as a master flag, returning `true` only if the input passes every single constraint. This granular reporting makes it incredibly easy to craft precise, context-aware error messages for the user
>

# **الشرح بالتفصيل**

وصلنا للسؤال الثامن في قسم **`4.5 Form Validation`**، وهو مخصص للتطبيق الفعلي والعملي على أشهر الخصائص التي تخرج من كائن الـ **`ValidityState`** عند كتابة كود ماليء بالقيود في الـ HTML: **`أشهر خصائص ValidityState`**.

بناءً على مثالك الممتاز:

HTML

```
<input required>
```

تعالي نتعمق في كيفية ترجمة هذا الحقل برمجياً داخل كائن الـ `ValidityState` وما هي الخصائص الأكثر تكراراً واستخداماً في المشاريع الحقيقية ومقابلات التوظيف.

## 1. فك شفرة حقل `<input required>` عبر الـ ValidityState

عندما تضعين سمة `required` على حقل الإدخال، فإن المتصفح يُفعّل داخلياً خاصية محددة جداً لمراقبة هذا القيد:

- **الخاصية المسؤولة:** **`valueMissing`**
- **سلوك الحقل:**
    - **إذا كان الحقل فارغاً:** ستكون قيمة `input.validity.valueMissing` مساوية لـ **`true`**، وتكون قيمة `input.validity.valid` مساوية لـ **`false`**.
    - **بمجرد أن يكتب المستخدم أي حرف:** تتحول `valueMissing` فوراً إلى **`false`**، وتصبح الحالة العامة للحقل `valid = true` (إذا لم تكن هناك قيود أخرى).

## 2. أشهر 4 خصائص في الـ `ValidityState` (التي لا يخلو منها أي مشروع)

في مقابلات العمل، سيسألكِ الممتحن: *"ما هي الخصائص التي تستخدمينها بكثرة في الجافاسكريبت للتحكم بالـ Validation؟"*. إليكِ الأربعة الكبار:

### 1. `valueMissing` (حالة الحقل الفارغ)

- **السمة المرتبطة بها:** `required`
- **مثال الاستخدام:** التأكد من أن المستخدم لم يتجاوز الحقول الإلزامية مثل اسم المستخدم، البريد الإلكتروني، أو كلمة المرور.

### 2. `typeMismatch` (عدم تطابق النوع)

- **السمات المرتبطة بها:** `type="email"` أو `type="url"`
- **مثال الاستخدام:** عندما يكتب المستخدم نصاً عشوائياً مثل `myname` في خانة الإيميل دون كتابة علامة `@` والامتداد الخاص بالإيميل. هنا المتصفح يرفع راية الـ `typeMismatch` كـ `true`.

### 3. `patternMismatch` (عدم تطابق النمط/التعبير المنتظم)

- **السمة المرتبطة بها:** `pattern` (والتي نكتب داخلها Regular Expression - RegEx)
- **مثال الاستخدام:** إذا كان لديكِ حقل مخصص لـ "رقم الهوية الوطني" أو "رقم بطاقة الائتمان" وتريدين التأكد من أنه يتكون من 14 رقماً بالتمام والكمال: `<input pattern="[0-9]{14}">`. إذا كَتب المستخدم أي شيء آخر، تضيء خاصية `patternMismatch` بالـ `true`.

### 4. `customError` (الخطأ البرمجي المخصص)

- **السمة المرتبطة بها:** دالة `setCustomValidity()` التي شرحناها سابقاً.
- **مثال الاستخدام:** إذا قمتِ بعمل فحص خاص بكِ بالجافاسكريبت (مثل التحقق من أن كلمتي المرور متطابقتين)، وكتبتِ رسالة خطأ مخصصة، فإن المتصفح يضع خاصية `customError` تلقائياً كـ `true` ليمنع إرسال الفورم حتى تقومي بمسح الخطأ.

## 3. مثال برمجي متكامل يجمع هذه الخصائص 🛠️

إليكِ كيف يكتب المحترفون كود جافاسكريبت ذكي مستنداً إلى أشهر خصائص `ValidityState` لإظهار أخطاء مخصصة بالكامل:

JavaScript

```
const myInput = document.querySelector("input");

myInput.addEventListener("blur", () => {
  // نقرأ تقرير الـ ValidityState الخاص بالحقل
  const state = myInput.validity;

  if (state.valueMissing) {
    console.log("الخطأ: الحقل مطلوب وممنوع تتركه فارغاً!");
  } else if (state.typeMismatch) {
    console.log("الخطأ: صيغة البريد الإلكتروني غير صحيحة!");
  } else if (state.patternMismatch) {
    console.log("الخطأ: المدخلات لا تطابق النمط المطلوب!");
  } else if (state.valid) {
    console.log("رائع! الحقل سليم وجاهز للإرسال.");
  }
});
```

## الكلمات المفتاحية للحفظ (Keywords)

- **`valueMissing`**: الخاصية المرتبطة مباشرة بالسمة `required`.
- **`typeMismatch`**: الخاصية المسؤولة عن كشف عدم مطابقة صيغ الإيميل والروابط (URLs).
- **`patternMismatch`**: أداة التحقق من الالتزام بالتعبيرات النمطية (RegEx).
- **`customError`**: العلم (Flag) الذي يرتفع عند صياغة أخطاء مخصصة يدوياً.

> **جملتك النموذجية في المقابلة:**
> 
> 
> "In a standard form, the browser maps HTML5 validation attributes directly to specific properties on the **`ValidityState`** object. For example, using a simple **`<input required>`** activates the **`valueMissing`** property, which evaluates to `true` if the field is submitted blank. Other highly common properties include **`typeMismatch`**—triggered when inputs don't conform to `email` or `url` types—and **`patternMismatch`**, which validates inputs against custom Regular Expressions defined in the `pattern` attribute. Programmatically listening to these specific properties allows us to bypass generic browser behaviors and deliver highly precise, accessible, and user-friendly validation messages."
>

### ما هو `novalidate`؟

`novalidate` هو خاصية توضع على عنصر `<form>` لتعطيل نظام التحقق المدمج في المتصفح (Native Validation).

مثال:

```
<formnovalidate>
  ...</form>
```

#### متى نستخدمه؟

- عندما تريد بناء نظام تحقق مخصص بالكامل باستخدام JavaScript أو إطار عمل مثل React.
- عندما ترغب في عرض رسائل خطأ موحدة بدلًا من رسائل المتصفح الافتراضية.

#### ملاحظة مهمة

تعطيل Native Validation لا يعني إلغاء التحقق من البيانات، بل يعني أنك أصبحت مسؤولًا عن تنفيذه بنفسك، مع ضرورة استمرار **Server-side Validation**.
